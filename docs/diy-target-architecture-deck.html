Your question, answered exactly

A sub-agent IS an MCP tool with intelligence in the middle.

You nailed it. Same contract everywhere: call → (eventually) response + receipt. The response can take seconds or an hour — that changes the plumbing (async, completion event), not the concept. There are just three flavors of the same thing:

Deterministic tool

e.g. archus.create_issue.
No judgment. Seconds. Returns ID + URL or a loud error. Never a silent ack.

Sub-agent (worker)

e.g. run_task("research posts").
LLM inside. Minutes–hours. Fresh context, budget, durable step log. Returns a structured result + receipts, then dies.

Governor (owner)

e.g. zenod.store_memory.
Persistent. Single writer of one state dimension. LLM only where taste is the product (filing, drafting). Serializes writes.

The only thing that changes vs today: these tools stop calling each other sideways. No governor routes to another governor. All calls fan out from a brain and all results fan back to it. That single rule is what kills the silent acks, the lost context, the "three front doors."

"What if I send two messages quickly?"

The mailbox rules

R1One conversation = one session = one turn at a time. Your two rapid messages queue up; the brain finishes its turn, then reads BOTH and answers once, with full context. no interleaved half-answers
R2Different conversations run in parallel. Your WhatsApp thread and a scheduled session don't wait for each other — separate mailboxes, separate brain turns.
R3Long work never holds the mailbox. The brain dispatches a worker and ends its turn. The worker's completion (with receipts) arrives later as just another message in the queue. this is why you can keep talking while things run
R4Everything durable. Mailbox and step logs survive restarts — a redeploy resumes turns and runs instead of killing them. I8-2, in flight tonight
R5Phylax paces the way back. Outbound to you is deduped and sequenced by one owner — no triple error bubbles, ever again.
User journey · the dev loop (what's literally running right now)

Backlog → execute → test → summarize → discuss

1You + the brain agree the iteration document (objective, tickets, acceptance criteria, tests). The doc is the brain's state — not a message between agents.
2Backlog sub-agent turns the doc into real tickets via archus.* — verbatim criteria, IDs + URLs back.
3Executor sub-agents in parallel, one per ticket. Each: fresh context, budget, durable log; PR auto-merges on green; appends a dated receipt to the doc. your "parallelize please" — this is where it lives
4Tester sub-agent (separate by design) runs the canonical board against the deployed build, appends the scoreboard. Fails must map to tickets.
5Summarizer sub-agent reads the doc + receipts: what worked, what failed, proposed next backlog.
6The brain discusses with you → iteration N+1 doc. Handoffs: the document and the tickets. Agent-to-agent chatter: zero.
