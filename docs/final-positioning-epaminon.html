What it is

Prompt-first, not ticket-first.

Epaminon dispatches real coding harnesses — Codex- and Claude-style CLI workers — against your repos, and brings back the evidence. No queue ceremony required: prompt in, durable result out.

Born, run, persist, destroyed.
Key positioning points

Why Epaminon, in five lines

  • A worker on tap. Buy execution like you buy compute: send prompt + effort, get result.
  • Honest isolation. Every job runs in its own ephemeral sandbox — arbitrary agent code never touches the shared container.
  • Minimum credentials. A sandbox carries only that job's creds and that tenant's scoped tokens. Nothing else exists inside it.
  • Durable evidence. Transcript and artifacts persist to your tenant storage; status and results queryable any time.
  • Zero idle cost. No always-on per-user executor burning RAM. Sandboxes exist only while jobs run.
The multi-tenant config

One API, ephemeral sandboxes.

A customer is a row

One always-on Epaminon API serves every tenant: queue, status, transcripts, evidence — all tenant-scoped behind your token.

The one sanctioned per-thing container

The suite's only per-something container is the sandbox-per-job: spun up for one job, destroyed after. Isolation where it matters, nowhere else.

Self-host = same image

The identical container with one tenant; your jobs, your box, your keys.

In the suite

The hands of the Council.

1

You — or Ring, or a briefing-governed suite like Herald — sends a task with an effort level.

2

Epaminon spins a sandbox, authenticates the worker CLI, and runs the job against your repo.

3

Transcript + artifacts persist to your storage; the receipt files into Zenod; the sandbox dies.

Boundaries

What Epaminon owns — and refuses.

  • Owns: execution, sandboxes, job transcripts and artifacts.
  • Never: owns the backlog (Archus), the memory (Zenod), the sending (Callisthenes), the routing (Ring).
  • Owns no repo by design. It works your repos with job-scoped credentials, then forgets them.
