Zenod · MCP hosting architecture

Selling MCP servers without 400 containers

The options, the recommended shape, and why it's simpler than what you have now — not scarier.

The one-line answer: the atomic DevOps unit for a sellable MCP server is one stateless HTTP service + one database + one secrets vault — not one container per customer. A new customer is an INSERT, not a deploy.

Where you are today (and why it hurts)

The current shape (Law 7)

One always-on container per user per unit, provisioned through Dokploy on a Stripe webhook. 100 users × 4 units ≈ 400 containers, each with its own subdomain, token, volume, repo, watchdog entry.

Why it's killing the dev experience

  • Every code change = M redeploys through a flaky Dokploy API.
  • Idle containers burn RAM (Callisthenes ≈ 549 MB each).
  • Watchdog registration, DNS, and provisioning machinery grow per user.
  • Hosted and self-hosted have drifted into two different products.

First correction: Phylax was never per-user

You caught this correctly. Phylax fronts one WhatsApp number. Many people talk to that one number. So there is one Phylax container per phone number you operate — probably one, total.

Adding a user =

Add their number to the whitelist. A config row. Not a deploy.

Why it still lives in its own container

Not for tenancy — for blast radius. Baileys is flaky and ToS-exposed; isolating it means WhatsApp breakage never touches the ring. That reasoning survives; per-user does not.

The DevOps atom for a sellable MCP server

This is the industry-standard shape for remote MCP (Streamable HTTP). It is what AWS, Cloudflare, and every MCP hosting platform converge on.

Stateless means

No per-user memory in the process. Every request carries a bearer token; everything tenant-specific is looked up from the DB/vault on each request. That's what lets one container serve 1 or 1,000 users identically.

Your fleet becomes

~5 containers total: zenod, callisthenes, ring, phylax, epaminon-api (+ Postgres). On one VPS. Forever, until real scale.

DNS & networking: it gets simpler, not harder

Today

A subdomain per tenant per unit: u1.zenod.dev, c-u1.zenod.dev, e-u1.zenod.dev… DNS records, TLS certs, and proxy routes multiply with users.

Multi-tenant

One hostname per unit. Five DNS records, total, forever:

  • zenod.zenod.dev/mcp/<token>
  • calli.zenod.dev/mcp/<token>
  • epaminon.zenod.dev/mcp/<token> …

The token in the URL identifies the tenant — your ZD-8 "the URL is the credential" design already works this way. Clients notice nothing.

Inside the VPS

One reverse proxy (Caddy/Traefik — Dokploy's built-in is fine) → one upstream per unit. No per-tenant routes. TLS is one wildcard or 5 certs.

Provisioning on Stripe webhook

Old: call Dokploy API, create compose, wait 1–2 min, hope it materializes, register watchdog, mint DNS.
New: INSERT INTO tenants, mint token, email the URL. Milliseconds. Nothing to watch.

Hosted vs self-hosted stop being two products

The complexity you're tired of — two divergent deployment stories — collapses. Multi-tenant code with a tenant count of 1 is the self-hosted product. One image, one docs page, one Dockerfile.

Zenod's git-repo state

The one stateful wrinkle. A multi-tenant Zenod keeps N clones under /data/<tenant>/repo on one volume. Same code path as today, path prefixed by tenant.

The target picture: your whole business on one VPS

How to get unstuck: the smallest path

Stop building

  • Per-tenant Dokploy provisioner & its failure recovery
  • Watchdog registration API for per-user instances
  • Per-tenant subdomain/DNS minting

Build instead (small)

  • 1. Add a tenants table (token_hash, plan, quota) to each unit. You have the bearer seam already.
  • 2. Prefix all storage by tenant: /data/<tenant>/…, WHERE tenant_id=.
  • 3. Point the Stripe webhook at INSERT + mint token + send URL.
  • 4. Epaminon: keep the API multi-tenant, spawn a throwaway container per job.

Order of attack

Callisthenes first — it's stateless key-custody + throttle, the easiest conversion and the cleanest proof of the pattern. Then Zenod (tenant-prefixed repos). Epaminon's API was headless anyway. Ring/Phylax barely change.

The reframe

You're not choosing between "simple but unscalable" and "scary but scalable." The multi-tenant shape is less machinery: no provisioner, no per-user DNS, no watchdog fleet, one deploy, hosted = self-hosted. It's the version of this product you can actually be un-tired in.

Law 7 amendment to record in the spine: "one container per unit, multi-tenant within; isolation exceptions: Epaminon job sandboxes (per-job, ephemeral) and Phylax (per phone number)."
