Epic 2.5 · Ring Spec Readout

What are we building?

The Ring is the cloud version of the working Console/Council experience: channels come in, the Ring routes the turn, and connected MCP servers do the work.

Final boundary: Phylax transports messages, Ring routes conversations, Zenod owns memory ingest including audio, screenshots, Drive, transcription, and digest.

The simplest model

One place talks to everything.

Channels WhatsApp, Telegram, web chat
→
The Ring Mailbox + router + control UI
→
Connected servers Zenod, Herald, Callisthenes, Archus, Epaminon, any MCP server

The Ring receives the message, sees the connected tools and their “when to use me” skills, then calls the right server. If something should become memory, Ring sends it to Zenod ingest.

The UI expectation

The Ring needs a real control surface.

The UI is not a dashboard for decoration. It is where the user connects channels and servers, tells the Ring when to use them, and chooses the fallback behavior.

WhatsApp config

Cloud WhatsApp is not QR pairing.

Cloud product

Managed WhatsApp gateway

The customer should not scan a personal WhatsApp QR. Cloud uses a hosted channel setup: platform number, customer number through a provider, or business-account connect. Phylax owns the plumbing.

Self-host / dev

Baileys QR pairing

The QR flow stays for self-hosting and dogfood because it is fast and already works. It should not be the default cloud buying experience.

Phone status

Gateway health

Provider, webhook URL, delivery failures, session health, reconnects, delivery receipts.

Media rule

Pass to Zenod

Phylax exposes media to Ring; Ring routes memory-bound media to Zenod ingest. Zenod archives, transcribes, digests, and files.

The Ring UI is the customer's control surface. Phylax is the channel gateway behind it: inbound to Ring, outbound from Ring, nothing more.

Common

What Ring owns

Endpoint, token, enabled/disabled, skill text, relay policy, test call, health, and the settings link. The guy owns deeper configuration.

The Ring is the switchboard, not the admin panel for every product. Each product has its own cloud settings page.

What changed

Old spec vs current spec.

Old

Fused Console/Council

  • Working WhatsApp Console exists.
  • Routing, memory, media, and tools are tangled together.
  • Settings are not productized for cloud tenants.
  • It proves the behavior, but not the product shape.
Current

Ring as cloud router

  • Phylax is a simple gateway.
  • Ring owns conversation routing and control UI.
  • Connected MCP servers come with skills and settings links.
  • Zenod owns memory media ingest and digest.

The wire contract stays the same: MCP, bearer tokens, receipts, loud errors, and traceable long-running work.

What the spec says today

The build list is now N-1 through N-8.

N-1

Ring router core

Every inbound message becomes a routed Ring turn, borrowing the working deployed Console/Council behavior.

N-2

Connect-a-server UI

Add, remove, enable, disable MCP servers and attach skill text.

N-3

Default route

Decide what the Ring does when a message is ambiguous.

N-4

Named pass-through

“For Herald” or “@Herald” forwards mostly unchanged to that server.

N-5

Channels

WhatsApp, Telegram, web chat, provenance, and Phylax handoff. Drive/media ingest belongs to Zenod.

N-6

Compose or relay

Per connected server: verbatim attribution or Ring-composed answer.

N-7

Provisioning

One Ring router plus Phylax plus default connected servers, watched and receipted.

N-8

Doc cleanup

Rewrite the old laws/catalog so the doc says one thing, not two.

Carried

W-H / W-I

Dispatch tracing and shared engine cleanup still matter.

Still unresolved

The five decisions are simple.

RP-1

How smart is Ring routing?

Recommended: borrow from the working Console/Council path, but keep memory ingest in Zenod and transport in Phylax.

RP-2

What is a skill?

Recommended: start with editable plain-language instructions per server.

RP-3

What is the fallback?

Recommended: Ring handles general turns by default, routes memory-bound turns to Zenod, and make the fallback configurable.

RP-4

How strict is “for Herald”?

Recommended: deterministic pass-through with minimal Ring thinking.

RP-5

Can Ring rewrite answers?

Recommended: per-server setting. Herald can be verbatim; tools can be summarized.

Meta

Is this the right UI?

This is the real product question: does the Ring feel like a control surface, an inbox, or both?
