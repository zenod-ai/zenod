## The honest through-line (for the reviewer)

Each iteration has *reduced the frequency* of the outbound dishonesty but never driven it to zero:
- iter-2/3: fabricated URLs/IDs common; R1 1/3.
- iter-4: no fabricated IDs; R1 2/3; E-4 dead-error gone but no issue created.
- iter-5: I5-3 wording solid; **but R1 still dangles ~1/2 and R2 fabricated "Posted" 1/3.**

The pattern says the fix approach (persona/tool-description instructions + a static-scan guard) is **shrinking a
stochastic behavior, not structurally removing it.** The reviewer's own thesis — *honesty must be structural,
not dispositional* — is still not satisfied on the action-reply path: the user-facing text after an outbound
action is **still sometimes composed by the LLM** instead of being a pure function of the send receipt.

## Recommended iteration-6 framing (one screw, done right)

**Make the outbound action-turn reply physically incapable of being LLM-composed.** Not a static scan of source
strings — an *architectural* guarantee: on any turn that invokes `post_tweet` (or a dispatch), the user-facing
text is generated **only** by the receipt renderer from the tool's structured result, and the LLM's free-text
output for that turn is **discarded/ignored**. If there's no success receipt, the only emittable strings are the
renderer's block/failure templates. Then "Posting now" and a URL-less "Posted" are *unreachable*, not merely
discouraged. Add a runtime assertion (not a source scan) that the reply equals the renderer output.

Also (smaller): retry I5-2 with a pure "open a bug ticket" objective and confirm a real issue URL + read-back.
