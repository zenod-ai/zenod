## Cause

Both alarms came from **stale installed copies on VPS3**, not from the repo. The smoke timer runs `~/.local/lib/zenod-smoke/smoke-prod.mjs` (copied 3 Nov), and the page probe runs `~/.local/lib/epic6-s1-health/{probe,aggregate}.py` (copied 10 Nov). M10 (11 Nov, root D28) already changed both rules in the repo, but nobody re-installed them:

- The old sha check compared **production** with the newest publish. Under D28, production moves only when the hourly promote runs, so every release went red after 30 min.
- The old poller check grepped only `deploy-poller zenod-mt`. Since D28, the VPS1 poller (`infra-vps-deploy-poller.timer`, every 5 min, unchanged) logs `deploy-poller zenod-staging: noop up to date`, and `zenod-mt` lines appear only during a promote. That is why the check was red from 11 Nov.

## Fix

1. Re-installed every page and smoke file from `main` (`cp scripts/smoke-prod.mjs ~/.local/lib/zenod-smoke/`, `cp docs/health/s1-live/*.py ~/.local/lib/epic6-s1-health/`). `docs/health/SMOKE.md` now says to install all `s1-live/*.py`, not only `smoke_view.py`.
2. Added the check `cloud.promote-lag`. M10's version had stopped checking production lag altogether. The new check reads the promote tick's own log (`~/zenod-eval/promote-schedule.jsonl`, EPIC-24 M12). It passes when production equals staging, and when the tick is waiting as designed (batching, hourly-limit, quiet-hours, paused). It goes red when:
   - the tick has been silent for more than 90 min (two missed hourly ticks), or
   - the last tick ended in `gate-failed`, `gate-failed-earlier`, `promote-failed` or `error`, or
   - 3 daytime ticks saw the same staging sha and none of them promoted it.

## Real stalls stay red (tests in `scripts/smoke-prod.test.mjs`, run in `ci`)

- The 19 Nov 17:31Z case (staging 11 min old, last tick `batching`) passes. Nine quiet-hours ticks pass, and so does a pause.

Live dry run before merge (worktree, real VPS1 and log): `cloud.deployed-sha` PASS, `cloud.promote-lag` PASS, `deploy.poller` PASS.
