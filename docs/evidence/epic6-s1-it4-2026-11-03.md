## How it works ([gate.py](../health/s1-live/gate.py), Dokploy app `zenod-health`, redeployed 2026-11-03 ~15:16Z)

- `GET /password` (signed-in only, else the sign-in form with `next=/password`): username field
  `autocomplete="username"` (read-only, `jordi`), two fields `autocomplete="new-password"`, so password managers offer
  to generate and save. `POST /password`: needs a valid session, rejects a foreign `Origin` (403, on top of
  `SameSite=Lax`), mismatched fields or fewer than 12 characters (400). It writes only
  `scrypt$16384$8$1$<salt>$<hash>` to `/srv/auth/password.scrypt` (VPS1 `~/.local/share/zenod-health/auth/`, dir 0700,
  file 0600, atomic replace). POST bodies are never logged (the log line is the request path only).
- Once that file exists the env password (`zenod-health/HEALTH_PAGE_PASSWORD`) no longer signs in, by form or Basic
  header. It stays a server secret: env password + stored hash key the session cookie, so a password change signs every
  other browser out and re-signs the one that changed it. With no hash the key is the iteration 2 key, so Jordi's current
  session was not cut by this deploy.
- **Sliding session**: any request with a valid cookie older than a day gets a fresh 30-day cookie. The page reloads
  every minute while open, so a browser in use never expires; one unused for 30 days asks for the password, which
  Bitwarden fills.
- One-time links (iteration 3) are unchanged, except that a link sign-in goes to `/password` while no password is set.
- [probe.py](../health/s1-live/probe.py) (VPS3 timer): page gains a "Set or change your password" link
  (https://health.zenod.dev/password) and the green box text says the browser stays signed in while used and that the
  link is also the recovery path.

**Recovery** (lost password): the tailnet page's one-time link still signs in; then "Set or change your password".
Last resort: `rm ~/.local/share/zenod-health/auth/password.scrypt` on VPS1 brings back the store password.
