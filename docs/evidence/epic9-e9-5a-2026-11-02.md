#1474 in detail:
- `packages/core/src/vault/memoryIndex.ts` keeps one SQLite FTS5 file per tenant at `<dataDir>/memory-index.sqlite`, beside the vault and never inside it (E9-A6 default).
- Rows cover pages, Log entries and Tree.md roots (the collapsed tree).
- Ranking is `bm25()` with column weights title/aliases 10, lineage 5, summary 3, body 1. A raw Log entry counts half against its digested page.
- The tokenizer is `unicode61 remove_diacritics 2`, with light suffix stemming and no Porter stemmer.
- Every hit carries its tree path. A Log hit is its exact evidence ref, with the path of the page it was filed on.
- Aliases: one built-in group to start (agentine ↔ agent team). Tenant aliases come from `- alias: A = B` lines under `## Keeper notes` in Tree.md, which is the hook for E9-5b.
- Freshness:
  - every write-queue task (a filing or a pull) marks the index dirty;
  - the next search re-reads only the files whose mtime or size changed;
  - a 60 s staleness check backs this up;
  - lineage of unchanged rows is re-derived when a parent moves.
- `zenod index rebuild | search <q> | stats` is the CLI. In the container: `node packages/core/dist/cli.js index rebuild` with `ZENOD_DATA_DIR=/data`.
- An index file stamped for another tenant is refused with `MemoryIndexTenantError`.
- `search_memory`, ask_brain's `search_vault` tool and the E9-3c host fallback all use the index first. The old two-pass scan stays the fallback when the index is absent, fails or finds nothing.
- `search_memory` ends its hit list with `Search: tier-0 index, N ms (rows, MB)`. That line is how the live numbers below were read without shell access to the container.

Tests are in `packages/core/test/memoryIndex.test.ts` (10). They cover:
- the index lives beside the vault;
- ranking, lineage on page and Log hits, root rows;
- built-in and Keeper-note aliases;
- accent folding;
- incremental add and delete;
- lineage re-derived when a parent moves;
- rebuild idempotency, including an incremental index converging to a fresh rebuild;
- tenant isolation, at the index and engine level;
- the scan fallback;
- ask_brain's search going through the index.

Suites: core 1182 passed, server 1435 passed, typecheck and schema check clean, CI green on both PRs.

| Model cost | $0 | no provider call anywhere in the index path |

Server-side time covers the index query plus any freshness refresh the query triggers: a no-change mtime check, or re-reading files after a pull or filing. It does not cover the vault pull or the tool's lineage pass.

**Margin is thin.** Three live runs gave p95 45.0, 48.2 and 46.1 ms, with a max of 53–60 ms. All three are under the target, but not by much. #1479 halved query time offline, yet live it moved p50 by only about 3 ms (28 → 25). So the production floor is set by something the offline vault does not reproduce. Likely candidates are refreshes after pulls and filings, or CPU shared with the other tenants on `zenod-mt`. The cause was not isolated. If a later row needs headroom, the next step is to put refresh time and query time separately on the `Search:` line.

The cold build after the #1479 deploy took 1.8 s (727 rows, 4.7 MB). The first deploy's cold build took 2.7 s.
