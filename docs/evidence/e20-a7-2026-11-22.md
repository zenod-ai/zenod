## 1. The service and its speed (vps3, 22 Nov, load 12 to 17)

A 30 s clip (a piece of the team's own bench audio; its text is not kept here), same request shape the server sends:

| model | time | note |
|---|---|---|
| small | 11 to 26 s | about half real time under load |
| large-v3-turbo | 33 s (twice) | about real time under load |

A 5.5 s clip (the team's narrator test line) at load 12: turbo 27, 28, 36 and 39 s, small 6 and 9 s. Turbo has a fixed cost of about
30 s under this load, so with the 60 s limit it fits notes up to about 30 s and small up to about 90 s. The server picks the
model by the note's length (`centralSttModelFor`): turbo up to 30 s, small up to 90 s, longer notes skip the service and go
straight to the paid provider (they could not finish in 60 s, waiting would only delay them). Both limits are env settings.

## 2. Change

- `packages/server/src/centralTranscription.ts` (new): the request (`POST` multipart, `x-caller: zenod`), the 60 s limit, the
  alarm line, a 2-minute cooldown after a timeout, network error or 5xx.
- `packages/server/src/transcribe.ts`: `runTranscription` tries it first for every caller (Phylax's shared transcription, chat
  channels, web mic, ingest), then continues down the unchanged cascade. A cancelled note writes no alarm.
- `phylaxUnit.ts`: `transcription.done` carries `central`; `shared_openai` is false for a note the central service wrote.
- `docs/health/s1-live`: row 21 counts the fallbacks (amber with one in 15 min, red with five).
- Tests (`packages/server/test/centralTranscription.test.ts`, 15): success (no paid call, no alarm), slow (a 150 ms limit in the
  test; the default is asserted to be 60 000), down (unreachable, 503, empty text, not JSON: fallback at once), alarm (fixed words
  only), cooldown and recovery, long note skips, small model for 100 s, cancel, off switch. Health: `test_aggregate.py`,
  `test_probe.py`.

## 3. The path from VPS1 containers (found on staging, 22 Nov)

| try | result |
|---|---|
| staging container, the name `vps3.taild81fbb.ts.net` | at once `[ops-alert] transcribe central_fallback reason=network`, the cause was hidden, so PR 1749 adds `cause=<code>` and a boot probe; the probe says `cause=ENOTFOUND` |
| staging container, tailnet IP `100.86.141.63:18946` (first try had a wrong env value, `NAME=value` instead of the value) | boot log `[central-stt] reachable` |
| staging, one test note (the team's narrator line, 5.5 s) through `/api/chat/voice/transcribe` with the staging test tenant | `[voice] web transcribe OK: provider=central faster-whisper large-v3-turbo`, text "No typing, no long messages. 10 seconds and the team is moving again."; the service log (`jobs.jsonl`) shows `caller zenod, model large-v3-turbo, audio_s 5.5, ms 29263`; the same request before had fallen back to the in-app whisper with the alarm line |

Cause: the Docker resolver in Swarm containers does not see MagicDNS names, the route itself works. So the three apps carry
`ZENOD_CENTRAL_STT_URL` with the tailnet IP (DEPLOYMENTS). infra-vps has a desk note (names will not resolve in containers;
the deploy poller skips staging as "diverged" since the history rewrite, so staging runs by hand pins until it is reset).
