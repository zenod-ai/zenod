## Cause, measured on a copy of Jordi's vault (2,352 Markdown files, 1,162 places, the same count the production log prints)

## Fix

`quickIndexBaseCached` (packages/core/src/vault/quickIndex.ts): the base is a pure function of the Markdown files and of the week window, so it is kept per vault keyed on the same fingerprint the memory tree uses (path, mtime, size of every `.md`; a file changed in the last 100 ms is never trusted; a failed build is not kept). The tick still pulls the vault first (freshness unchanged), so a note filed anywhere changes the fingerprint and the next tick rebuilds exactly as before. Saves, search, chat and the quick-index model passes are untouched.

## Round 3: the 40 s block and the silent ticks (run run_8e0a09c6, PR [#1735](https://github.com/zenod-ai/zenod/pull/1735))

**Answer: the block was a cold search reading the memory index from disk one page at a time on the main thread; it is now read ahead off the main thread. Every tenant now logs its tick with CPU, and a vault with no tree is no longer pulled every 5 minutes. Live numbers follow below.**

**How the block was found (read-only).** `docker logs` for 13:00-13:03Z: one `search_memory` of 41,821 ms, `event_loop.lag` max 40,164 ms, utilization 0.61, and no log line from any other request between 13:01:04 and 13:01:46 (the loop was held). VPS1's own forensics log (`/var/log/vps-forensics`, 1-minute samples) for the container's cgroup in that minute: CPU 0.16 cores, read rate 4.4 MB/s, I/O pressure 24%, page cache 85 -> 301 MB. The 07:06Z block (41.8 s) has the same shape: 0.12 cores, 3.3 MB/s, 15.6% pressure. The host has 7.7 GB with 262 MB free and swap in use, so the index file (34 MB) and the vault leave the cache again and again. `node:sqlite` is synchronous, so each page it misses is one blocking read on the thread that also serves chat, WhatsApp and the web, and serial random reads at about 1 ms each add up to tens of seconds. The disk itself was calm in M24's sar (await 1.5 ms): a serial reader never queues, so the disk looks idle while the loop waits. No synchronous git, `execSync` or sync file call is on this path (git runs as a child process, the vault files are read async).

**Could not be reproduced here.** On VPS3 the same search on a copy of the vault (3,786 rows, 22 MB) is 460 ms cold or warm with 40 ms of loop lag: the local disk answers a page in microseconds. The cause above is the production signals plus the code path, not a lab reproduction; the live re-measure decides.

**Fix.** `MemoryIndex.primeFileCache` (packages/core/src/vault/memoryIndex.ts): before a search or a refresh the index file and its WAL are read once, in 1 MiB chunks, on the thread pool (at most once per 15 s, shared by parallel callers, never for an in-memory index), so SQLite's synchronous reads find their pages in cache and the loop keeps serving while the read runs. `synchronous = NORMAL` on the index (derived from the vault and rebuilt from it; WAL + NORMAL cannot corrupt, a lost tail is re-read). Any synchronous section over 1 s (search query, write, warm) logs `[memory-index] sync section held the loop N ms in <label>`; `[memory-search]` now prints for any search over 1 s even with no hits and carries `sync query N ms`. What is saved, ranked and returned is unchanged.

**Tick.** `[quick-index] tick tenant=T ... result=ok|no-tree|no-vault|error cpu=Xms child=Yms personas=Zms`: one line per tenant per tick (`cpu` is the Node process over the tick, all threads; `child` the git calls it waited for, from `/proc/self/stat`). A vault with no Tree.md is looked at once an hour (`engine.quickIndexBase`: no pull, no file listing in between). Each tenant's first tick lands at its own point of the first interval (at least a minute after boot), so the seven runtimes no longer tick in one burst and a tick's CPU is mostly its tenant's. An unchanged quick-index state is not rewritten. The helper check is a handful of store reads and stays as it is; its time is on the line (`personas=`).

**Tests.** memoryIndex: loop stays free while a 24 MB file is read ahead, missing files are skipped, one read-ahead per window under a burst of 20 searches, same hits with and without it, `synchronous = NORMAL`, the 1 s warning (6). quickIndexPhases: no-tree skipped for an hour then a tree that arrives on the remote is found (1). quickIndexTick: a line per outcome (no-vault, no-tree, error, ok), line format, CPU marks incl. a child process, spread clocks, one tick per interval, no rewrite of unchanged state (9). Server suite 1989 + 9 pass (13 failures seen under three parallel suites were load timeouts; the files pass alone), chassis 116, core touched files pass.

The main thread writes a heartbeat into shared memory once a second; a worker thread checks it each second and, when it is older than 5 s (`EVENT_LOOP_WATCHDOG_MS`, 0 turns it off), connects to the main thread with `node:inspector`, pauses it, reads the call stack, resumes it and writes one line straight to stderr (a worker's console goes through the blocked main thread, so it would appear only after the freeze): `{"level":"warn","event":"event_loop.blocked","held_ms":N,"still_held":true,"threshold_ms":5000,"stack":["fn (dir/file.js:line)", ...]}`. Function names and `file:line` of our code only, never a variable, scope, note or person. One line per block. When the main thread sits inside a native call (a synchronous disk read), V8 can stop it only as the call returns, so the stack names the code that made the call and `held_ms` says how long the loop had been held. Idle cost: one timer a second on each thread. Tests (5): the spinning function is named, a blocking native call's caller is named, one line per block and a second for a second block, nothing under the threshold, env and off switch. Read it live with `docker logs <zenod-mt> 2>&1 | grep event_loop.blocked`.

**Index base kept per file.** `quickIndexBaseCached` now derives each tree page (tree fields, summary, aliases, citations, date) and each Log day (entries cut to the nickname excerpt) once, keeps it per file keyed by mtime and size (a file written within 100 ms of its stat is never kept) and saves it to `quick-index-base.json` beside `memory-index.sqlite` (never in the vault; 0600; unreadable, other-version or other-vault files are ignored). Everything that crosses files (tree shape, which citations are agent reports, counts, the week window) is recomputed each build from those. The tick line gains `files=<read again>/<reused>`. Synthetic vault of 1,190 files on VPS3: full build 535 ms wall and 820 ms CPU, first build with the memo 374 ms, after a restart 52 ms, after one save 40 ms. The real vault is about twice that and VPS1 several times slower, so the live numbers decide.

**Fix (PR [#1739](https://github.com/zenod-ai/zenod/pull/1739), merged bfa96fc8, `ci` green; not yet promoted).**
- `captureReceiptsAsync` runs the scan on a worker thread with its own connection (WAL: a reader does not block the writer). Identical concurrent reads share one scan, at most two scans run at once, and a worker that cannot start falls back to the old synchronous read. Only the caller waits.
- With an evidence ref (`get_memory`, the note read) the query checks `instr(result_json, <ref as JSON writes it>)` before any JSON parse, so one note no longer parses every other job's text.
- The row-to-job mapping and `mergeMemoryEntriesAsync` hand the thread back every ~20 ms and give the same entries as the synchronous merge.
- `search_memory`, `get_memory` and the subscriber notes API use them.
- Tests (`captureReceiptsMemory.test.ts`, 5 new): same receipts as the sync read for all and for one ref, including a quote and unicode ref; one shared read; on 5,000 jobs of 22 KB the loop is never held over 250 ms by the read; the merge never over 150 ms with a 1 ms note read per job; in-memory store falls back.
