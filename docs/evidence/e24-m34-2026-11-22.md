Objective: Zenod: 5 testers: a Zenod that burns a core when idle slows the shared VPS1 the team and the testers' WhatsApp run on. Run run_79c5723b-8381-46dd-896b-c1cf02a337bb. Content-free: counts, timings and code paths only.


Cause of the first spike, from the earlier run: every 5 minutes each tenant's clock rebuilt the whole quick index from the vault (every page and every Log file), about 2.3 s of CPU on VPS3 and 14-19 s on VPS1. ## Cause, measured on a copy of Jordi's vault (2,352 Markdown files, 1,162 places, the same count the production log prints)

`quickIndexBase` on VPS3: 2.1-2.3 s CPU per call warm (3.7 s cold), profile dominated by reading and parsing every page (`quickIndex.js` page loop, YAML parse). VPS1 is slower and shared, and the same tick also runs after each tenant pull, hence the larger 14-19 s there (not separated further: the container has no profiler we may attach). `loadMemoryTree` is already cached by vault fingerprint (M7); the quick index base was not.

## Fix

`quickIndexBaseCached` (packages/core/src/vault/quickIndex.ts): the base is a pure function of the Markdown files and of the week window, so it is kept per vault keyed on the same fingerprint the memory tree uses (path, mtime, size of every `.md`; a file changed in the last 100 ms is never trusted; a failed build is not kept). The tick still pulls the vault first (freshness unchanged), so a note filed anywhere changes the fingerprint and the next tick rebuilds exactly as before. Saves, search, chat and the quick-index model passes are untouched.

| Test (packages/core/test/quickIndex.test.ts, 4 new) | Result |
|---|---|
| Unchanged vault: same object, equal to a fresh build | pass |
| File changed / new week: rebuilt with the new counts | pass |
| Racy file (just written): never reused | pass |
| No tree: null, nothing wrongly kept | pass |

Local measurement on the vault copy (VPS3): idle tick 2.3 s CPU -> 0.04-0.11 s. `tsc` clean, quick-index and memory-index tests 49 of 49, `ci` green.

### What still spins

1. **The tick's remaining 6-8 s.** It is not the quick-index base any more: the base is cached and a stat of 2,352 files was measured at 0.04-0.11 s on the vault copy. The tick still runs `syncForRead` (git pull of the GitHub vault: fetch, merge, index) before the cache check (`engine.quickIndexBase`, engine.ts:4288), then `updateQuickIndex` and the read-as view, and the container has no profiler we may attach, so the split is not measured. The pull is the likeliest share. A next step is to log the tick's phases (pull, fingerprint, update) in milliseconds, then skip the pull when the vault has no new commits (`git ls-remote` is a few ms of CPU).
2. **The team's own ticket-context search burst.** In 10:00-10:09 the team's console fetched ticket context with about 87 memory searches in 9 min (`agent-team/ticket-context` user agent), each one refreshing the 33.8 MB tier-0 index (refresh up to 4.7 s) and running in parallel, which kept the container at 50-100% of a core for nine minutes. That is use, not idle, but it is the biggest CPU on VPS1 during a wake, and it can be cached (one tier-0 refresh per vault fingerprint, shared by parallel searches) or paced on the caller side.
3. **Filing a save.** Unchanged, as noted below: 10-45 s CPU per save on VPS1 (classify, compose, enrich, media ingest), the part of the 25% windows.

## Round 2: the three fixes (run run_675262be, merged 2c12217a, PR [#1732](https://github.com/zenod-ai/zenod/pull/1732), `ci` green)

```
tick of one tenant        before                         after (this change)
 pull                     fetch + merge every 5 min      ls-remote (one ref line); fetch only if the head moved
 index base               cached (round 1)               cached (round 1), its stat time now logged
 phases in the log        none                           one line: pull head/fetch/merge, stat, rebuild, update, total (ms)
parallel searches         each: a full vault read,       one shared refresh: a burst of 40 runs 1 read
                          queued one behind another      (old code: 40, measured in the new test)
```

- **Tick log.** Each tenant's 5-minute tick writes `[quick-index] tick tenant=<id> pull=<ms>(skipped|fetched|recent|busy) head= fetch= merge= stat=<ms> rebuild=<ms>(cached|rebuilt) update=<ms> total=<ms>`. Timings only, no name or text. This answers "what is the 6-8 s" exactly.
- **Pull skip.** `VaultRepo.pullForFiling` lists the remote head ref and fetches only when it differs from the commit already held; a moved remote, an error or no tracking ref takes the old full path; a clone that fetched earlier but never merged still fast-forwards; a prepared local commit is left alone. The Drive vault is not changed (its manifest check is a different cost).
- **Shared refresh.** Searches join the one queued tier-0 refresh, or the running one when no write marked the index dirty since it began (a write marks dirty after its files are on disk, so a search after a save still waits for a refresh that started after the save). A failed shared refresh is retried once by each search.
- **Tests.** 5 pull-skip, 3 shared-refresh (burst of 40 reads the vault once, a write during a burst is seen, a failed refresh does not poison the next searches), 1 engine phases, 1 log line. `tsc` clean; server suite 1989 of 1989; core suite 1457 of 1459 run, the other 2 (`engine.test.ts`, a gitleaks finding on a test fixture) fail the same on unchanged `main` on VPS3; `ci` green in 14 min.
- **Not changed.** A save's own filing cost, chat replies, search ranking and results.
