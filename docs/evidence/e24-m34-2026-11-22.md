# EPIC-24 M34 evidence: zenod-mt burned CPU with nobody using it (2026-11-22)

Objective: Zenod: 5 testers: a Zenod that burns a core when idle slows the shared VPS1 the team and the testers' WhatsApp run on. Run run_79c5723b-8381-46dd-896b-c1cf02a337bb. Content-free: counts, timings and code paths only.

## Answer

The 68% alpha9 saw (22 Nov 05:26-05:48Z) was mostly the M31 backlog (260 requeued enrichments, about 10 s each, on a container up since 05:14Z). Once that drained, an idle zenod-mt still did one real chore: **every 5 minutes each tenant's clock rebuilt the whole quick index from the vault** (every page and every Log file), even when nothing had been filed. On Jordi's vault that is 14-19 s of CPU per tick on VPS1. Fix: rebuild it only when a Markdown file changed. Merged `955bd353` (PR [#1729](https://github.com/zenod-ai/zenod/pull/1729), `ci` green); live on production after the tick promotes it.

```
before (idle tick, every 5 min)               after (idle tick)
 clock -> pull -> read ALL pages + Log         clock -> pull -> fingerprint (stat of every .md)
          parse, 1162 places  ~2.3 s CPU here           unchanged -> reuse the base   ~0.05 s CPU
          = 14-19 s CPU bursts on VPS1                  changed   -> rebuild as before
```

## Before: production zenod-mt (container up since 06:52Z, 4-core VPS1, load 4-6)

Read-only: cgroup `cpu.stat` of the container (15 s samples, 07:52-08:02Z, 586 s) and the allowed `docker logs` form.

| Measure | Value |
|---|---|
| Average over 586 s | 10.5% of one core (docker stats between bursts: 0.3-5%) |
| Since boot 06:52Z (770 s of CPU in about 85 min) | about 15% |
| Bursts above 50% | 3 in 10 min: 07:53:21 (about 17 s CPU), 07:58:22 (about 14 s), 07:59:22 (about 19 s) |
| Between bursts | 1-4% |
| Event-loop warnings 07:05, 07:26, 07:46Z | one block of 41.8 s, 9.0 s, 8.7 s in a minute (`event_loop.lag`, M24 monitor) |

The 07:53 and 07:58 bursts are 5 min apart with no log line and no request: the tenant clock (`startTreeSweepSchedule`, 5 min, runtime.ts) calling `refreshQuickIndex` -> `engine.quickIndexBase()`. The 07:59 burst follows a team `store_memory` call (a real save, about 19 s CPU before the job finished; its own cost is filing work and was not changed here). Nothing else spins: no recovery retry, no weekly sweep, no poll in the log; the log is almost silent between those moments.

## Cause, measured on a copy of Jordi's vault (2,352 Markdown files, 1,162 places, the same count the production log prints)

`quickIndexBase` on VPS3: 2.1-2.3 s CPU per call warm (3.7 s cold), profile dominated by reading and parsing every page (`quickIndex.js` page loop, YAML parse). VPS1 is slower and shared, and the same tick also runs after each tenant pull, hence the larger 14-19 s there (not separated further: the container has no profiler we may attach). `loadMemoryTree` is already cached by vault fingerprint (M7); the quick index base was not.

## Fix

`quickIndexBaseCached` (packages/core/src/vault/quickIndex.ts): the base is a pure function of the Markdown files and of the week window, so it is kept per vault keyed on the same fingerprint the memory tree uses (path, mtime, size of every `.md`; a file changed in the last 100 ms is never trusted; a failed build is not kept). The tick still pulls the vault first (freshness unchanged), so a note filed anywhere changes the fingerprint and the next tick rebuilds exactly as before. Saves, search, chat and the quick-index model passes are untouched.

| Test (packages/core/test/quickIndex.test.ts, 4 new) | Result |
|---|---|
| Unchanged vault: same object, equal to a fresh build | pass |
| File changed / new week: rebuilt with the new counts | pass |
| Racy file (just written): never reused | pass |
| No tree: null, nothing wrongly kept | pass |

Local measurement on the vault copy (VPS3): idle tick 2.3 s CPU -> 0.04-0.11 s. `tsc` clean, quick-index and memory-index tests 49 of 49, `ci` green.
