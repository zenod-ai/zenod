# EPIC-20 A5: WhatsApp reconnects by itself after a slow credential save (incident 19 Nov 2026)

Objective: Zenod: 5 testers: WhatsApp is how testers and Jordi reach Zenod; after a disk hiccup it now comes back by itself instead of staying down for hours.

```
 disk stalls ──► socket closes (408) ──► credential flush > 2 s
                                           │
   before: throw ──► state "error", no timer ──► down 3 h (manual restart 14:46Z)
   now:    keep save as backlog ──► reconnect 2 s, 4 s … 60 s, each waits for the save ──► connected
                                           │
   still red 5 min ──► watchdog line in Zenod's desk inbox (plus the HQ page it already sent)
```

alpha9's check saw it red from 12:11Z; the gateway was actually down from 11:43:53Z.

## 2. Why it stuck

`handleConnectionClose` (packages/server/src/whatsappGateway.ts) did `await this.flushSocketCredentials(socket)` and only then `this.scheduleReconnect(...)`. The flush races Baileys' save queue against a 2 s timer and rethrows on timeout, so the throw skipped `scheduleReconnect`. The caller in `bindSocket` caught it with `closeWork.catch(...)`, which set `state = "error"` and nothing else: no timer, `nextRetryAt` null. Nothing ever called `start()` again. Swarm did not restart it either: the Phylax service has no health check, so `/api/health`'s `restart.required` was never acted on.

## 3. The fix (PR [#1707](https://github.com/zenod-ai/zenod/pull/1707))

- The close path calls `retireSocketCredentials`, which never throws. A save still writing after 2 s becomes a backlog; each reconnect first waits up to 15 s for it (an async wait, the event loop never blocks), so older credentials can never overwrite the new socket's. A save that failed outright has already put the last good copy back (`creds.last-known-good.json`). Nothing deletes the session.
- Reconnects back off 2 s, 4 s, 8 s … capped at 60 s and reset when the link opens. A failed attempt, or any unexpected close-handler error, schedules the next one; only logged-out / bad-session stay terminal (they need a re-pair).
- New health events: `credential_flush_slow`, `credential_flush_pending`, `credential_flush_recovered`, `credential_flush_failed`; `reconnect_scheduled` now carries `attempt`.

## 4. The alarm (which path: the zenod watchdog on VPS1, the M21 desk path)

Already wired: the VPS1 user timer `zenod-health-watchdog.timer` (every 2 min, `scripts/watchdog/zenod-watchdog.sh`) checks row-4 `phylax.zenod.dev/api/health` = 200 "ok" with WhatsApp `connected`, and pages the HQ queue at once. That queue wakes nobody (EPIC-24 M21). New: a row in `ZENOD_WATCHDOG_SUSTAINED_KEYS` (default `row-4=300`) red for 5 minutes or more also joins the daily `public-outage` note in Zenod's own `desk/inbox`, which the Delivery Manager's next wake reads. Phylax's own health event was not used: nothing consumes it yet.
