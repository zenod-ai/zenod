## What expires

- One env stamp on Dokploy `zenod-mt`: `ZENOD_GOOGLE_DRIVE_VAULT_OAUTH_VERIFIED_AT`, set 2026-08-30T15:48:22Z.
- It feeds the readiness check `google_drive_vault_oauth` (`packages/server/src/productionReadiness.ts:86`), which
  is true only while the stamp is under 90 days old: **false from 2026-11-28T15:48:22Z**.
- It is our own gate, not a Google expiry. Google does not expire anything for the `drive.file` scope: it is a
  non-sensitive scope with no yearly re-verification. The stamp records that a person looked at the Google Cloud
  project (exact Drive OAuth client, redirect URI `https://cloud.zenod.dev/api/vault/drive/oauth/callback`,
  branding, `drive.file` scope, publishing status) in the last 90 days.

## What happens if it lapses

- `google_drive_vault_oauth` is not advisory, so `/api/public/production-readiness` turns `ready:false` and
  `checkoutEnabled()` closes paid checkout for every new person, the €0 tester code included.
- Existing subscribers and their Drive vaults keep working: the check only gates checkout.
- Only owners on `ZENOD_LIVE_CHECKOUT_TESTER_GOOGLE_EMAILS` / `_GITHUB_IDS` / `_USER_IDS` can still check out.
  The E26-S2 auto-accept flow does not add accepted testers to those lists (only env reads them), so every tester
  accepted after 28 Nov would hit a closed checkout.
- The VPS1 readiness watcher (EPIC-7 T2.3) warns from 2026-11-21 and alerts at expiry.
