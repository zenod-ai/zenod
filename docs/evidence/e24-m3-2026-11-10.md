## Round 2 (06:00–08:00 UTC)

**Bottom line: two causes found and fixed. The 50 voice notes saved this morning but never filed were stuck behind a restart (fix live as 943e30d since 07:11 UTC) and are being filed once each. The memory crash was a search cache that kept old vault text alive after each filing, on any model, not just DeepSeek (fix cfd0fc3).**

Counts and kinds only. No note content, no tenant id and no page paths are on this page.

### Why the 50 notes were never filed

- All 50 are voice notes saved through MCP between 00:50 and 01:10 UTC (47 recorded on earlier days, from agent_team's back-fill). Each got a filing job.
- Between 00:12 and 02:05 UTC production restarted six times: releases at 00:12, 01:20, 01:42 and 02:04, and out-of-memory crashes at 01:00:50 and 01:18:52 (both found in the host log today; round 1 only knew of the 04:00 ones).
- A restart can cut a filing off half-written in the vault. The new process then starts its queue at once, and every waiting filing job saw the other filing's leftover changes and stopped with a permanent error (`filing_unrecognized_local_changes`). Saves that hit the same state got a recoverable error and were retried. Filing jobs did not.
- The vault history shows it: after the 01:42 release, recovery replayed the cut-off filing at 01:46:37 and the blocked saves at 01:47:36–01:48:05. None of the waiting filing jobs ever ran again.
- The production sweep confirms it: all 50 entries still had a filing job, and every one of those jobs had ended without filing.

### What changed (PR #1588, merged 943e30d, live 07:11 UTC)

- A filing job that finds another filing's leftover plan now waits for vault recovery and runs afterwards. It no longer fails for good.
- A process that is shutting down for a release takes no new job, so a release no longer starts a filing it will cut off.
- New operator path: setting `ZENOD_REFILE_UNFILED_SINCE=<day>` on the app makes Zenod, 60 s after start and for the operator's account only, find every Log entry since that day that has no `filed:` line, no filing receipt and no page citing it. Each one gets filing once: its old job is put back without the per-note chat message, or a new job is queued. Each is marked so the sweep never repeats it. The only log line is the counts. Undo: remove the variable.
- Tests: `packages/server/test/filingSweep.test.ts` (five cases). The two cause tests fail on the old code. CI green.

### The memory crash: found and fixed (it was never DeepSeek)

- At 07:22:53 UTC production ran out of heap again, **on OpenRouter**, after 10 filings in a row from the sweep. So the crash follows the number of filings in a row, not the model. DeepSeek only filed faster. Every crash today came during a burst of filings: 01:00, 01:18, 04:00, 04:04, 05:42, 07:22.
- Reproduction, zero spend: Zenod's real filing pipeline on a copy of the vault, with a stand-in model. After each filing the heap held 8 to 14 MB more than before (43 MB after the first filing, 113 MB after the eighth). With the ~256 MB heap production had, that is about ten filings.
- Heap snapshots after filing 2 and filing 8: the 60 MB of growth is text, held by the search text cache (E15-Q4). The cache keeps lines that are slices of whole file reads, and in Node a slice keeps the whole original text alive. The cache's size cap counted a few characters per line while megabytes stayed pinned.
- Fix (PR #1592, merged cfd0fc3): the cache keeps its own flat copy of each line. The same reproduction now stays flat at 32 to 33 MB after every filing, over 12 filings. A new test fails on the old code (76 MB kept) and passes with the fix.
- Guard while the fix rolls out: zenod-mt memory raised from 320 to 640 MiB at 07:36:53 UTC with the dokploy wrapper (one redeploy, same image). VPS1 had 3.2 GB free. Undo: set it back to 335544320 and redeploy.

## What #1584 fixed (real, but not this crash)

When a filing answer has uncertain or new-page topics, the catalog fallback used to run up to 8 vault searches at once. Each one buffered every ripgrep match line of the vault, and a shared text cache was capped by entry count only.

- Repro on a 49 MB synthetic vault, the real `classifyCandidates` path, a stub model returning 8 uncertain topics, 200 MB heap: before the fix, heap out of memory with 691 MB RSS. After the fix it completes with a 58 MB peak heap and 166 MB RSS.
- The fix: searches run one at a time; a body search clips lines to 1,000 characters, keeps 200 lines per file and stops at 4 MB; the cache is capped by size.
- Why it was not the production cause: his vault is small (796 notes, 11.5 MB, the largest note 219 KB). On a vault that size these searches use tens of MB, not the ~150 MB the crash needs.

## What the two crashes share

- Both came right after a DeepSeek **first-pass** classify (stage `bounded-candidates`) succeeded: 10 s after it at 04:04, 3 s after it at 05:42. Neither reached the second classify call or reconciliation.
- Between those two points: candidate refinement (vault search and branch context), the decision checks and span resolution. I measured branch context on large sections and it stays under 31 MB.
- At 05:42 the heap held 253 MB after a full GC. The app starts at about 104 MB RSS.
- With filing on OpenRouter the same notes have filed without a crash (04:07–05:23, and since 05:44). Something in DeepSeek's answer shape or path makes the host blow up. One switch also differs: the quick index's model only runs when filing is on DeepSeek. It ran cleanly at 05:38:59, so it is not the trigger, but its memory adds up while it runs.

**Next step:** capture a heap snapshot or a `--heapsnapshot-near-heap-limit` dump on a copy that runs DeepSeek filing on a copy of this vault, so the allocation shows up directly. Guessing from the logs has run out.
