Design note · Answers two questions

Phylax already speaks MCP. And the sink can talk.

You asked two things: is Phylax really Ring-specific, or is it a general MCP client that should let you pick its sink in settings? And if voice notes go straight to memory, doesn't the experience collapse into a dumb sink you can't talk to? Answers, grounded in the code: Phylax is generic except for one hardcoded string, and the sink is only dumb if the receipt is dumb — Zenod's receipt already isn't.

Prepared 29 July 2026 Grounded in main @ 74ac96a Phylax = transport · Zenod = memory

Question 1 — Is Phylax general, or does it expect a Ring?

It expects an MCP server. This is not a proposal — it is what the code does today. Phylax's downstream is callPeerTool(url, token, tool, args): a plain MCP tool call against a per-tenant URL and bearer token that already live, encrypted, in tenant settings. The only Ring-specific thing in the entire seam is one hardcoded literal: 

// packages/server/src/phylaxChannels.ts
export interface PhylaxDownstreamCall {
  tool: "chat_with_ring";        // ← the one hardcoded string
  ...
}
...
downstream = await (this.options.callDownstream ?? callRing)(call);

async function callRing(call) {
  return callPeerTool(
    { url: call.route.downstreamUrl,      // ← already per-tenant config
      token: call.route.downstreamToken },// ← already per-tenant config
    call.tool,                            // ← always "chat_with_ring"
    call.arguments,
  );
}
Phylax is a generic MCP client wearing a Ring-shaped name tag. Your design — point it at any MCP server, discover the tools, bind one — is not a redesign. It is deleting one string literal and promoting it to configuration.

And the other end already fits: Zenod's MCP endpoint exposes store_memory (content, hints, verbatim → jobId), and Phylax polls get_task_result until terminal to get the evidence ref, pages touched, commit SHA — and, importantly for Question 2, a question from the librarian when filing is unclear. There is even ingest_memory for handing over raw audio artifacts, if you ever want Zenod to own transcription too.

The settings design: a sink you configure, not a peer you hardcode

This is the "MCP without a model" idea made concrete. MCP stays the universal socket between units — but the tool choice happens once, at config time, by you, in the settings page. Runtime stays completely mechanical. Full MCP generality, zero runtime interpretation.

Three properties fall out of this shape. Swappability: the day Ring is trustworthy, rebind text turns to it — no deploy. Independence: the voice-note row never touches Ring, so no Ring regression can ever lose a note again. Honesty: the settings page shows you your architecture instead of hiding it in a string literal.

Question 2 — "So it's a dumb sink and I can't talk about my note?"

This worry assumes the reply is "okay, stored." It shouldn't be, and it doesn't have to be — because Zenod's terminal receipt is already rich: a summary, the pages it filed to, the commit link, and a clarifying question when the librarian is unsure. The receipt is not the end of the conversation. It is the opening move of one.

The design is two lanes in one WhatsApp thread. Storage is the guaranteed lane. Conversation is the smart lane. They interleave in the same chat, and the smart lane reads what the guaranteed lane just wrote.

The whole flow, end to end

1 · Custody Phylax

Provider message, artifact, tenant, idempotency key. Supervised process; staleness restarts it.

2 · Speech STT

OpenRouter. Failure replies "couldn't transcribe — resend?" in seconds. No silent fallback.

3 · Bind Rule table

Turn type → configured MCP tool. A lookup, not a decision. No model, no regex, no guard.

4 · Store Zenod

store_memory → poll get_task_result to terminal. Queued ≠ saved.

5 · Receipt Phylax reply

Recap + pages + commit link + librarian's question, from the terminal receipt. Template, not prose model.

Compare with the incident path: the old flow's step 4 was Ring guard re-interprets your English — the one red box, and the only one that had no reason to exist for this journey. Every box above is either infrastructure or a lookup.

What this is not giving up

Kept, and strengthened

  • MCP as the only seam between units — now visible in settings.
  • Ring, as the future conversational front door — rebindable in one dropdown when it's ready.
  • Multi-agent on shared Zenod memory — every agent reads what capture wrote.
  • Receipts-or-silence: "saved" only ever comes from a commit SHA.

Given up

  • One string literal: tool: "chat_with_ring".
  • The idea that an interpretive layer must sit in the capture path.
  • Nothing else.

Build list — small, ordered, each shippable alone

1

Promote the tool binding to tenant config

Replace the hardcoded chat_with_ring with a per-turn-type binding (turn type → tool + argument template) in phylaxTenantSettings. Default stays exactly today's behavior, so this ships as a no-op.

2

Settings UI: discover and bind

In the existing Phylax settings panel: MCP URL + token (already there), a "discover tools" call (tools/list), and the binding table above. The dropdown is populated by discovery, never typed by hand.

3

Terminal polling + receipt template

For async tools (jobId responses), Phylax polls get_task_result with a deadline and renders the terminal receipt through a fixed template: recap, pages, commit link, question relay. Bind voice notes to store_memory, flip the switch, and the two real voice notes you're waiting on land in memory.

4

Later: the reflection toggle

One optional best-effort ask_brain reaction after the receipt. Off by default. Never blocks, never replaces the receipt. Ship only after 1–3 have survived a week of real use.
