## Step 1: enable T3's browser on VPS3

- `t3agent` has no sudo on VPS3 by design. Root came through the documented route from infra-vps `docs/vps3-faq.md` ("Root on VPS3 for an agent", via VPS1 and the `vps3_idle_ed25519` key).
- Ran as root at about 02:10Z: `/home/t3agent/.local/bin/t3 browser setup --base-dir /home/t3agent/.t3`. Output: "Allowed Chrome's sandbox for T3's browser. This host is ready for T3's browser."
- **What changed:** one new AppArmor profile, `/etc/apparmor.d/t3-chrome-headless-shell` (a before/after `ls /etc/apparmor.d` diff shows only this file). `kernel.apparmor_restrict_unprivileged_userns` is still `1`, so the host-wide restriction is untouched and only T3's Chrome binary is exempt.
- **Revert** (as root on VPS3): `apparmor_parser -R /etc/apparmor.d/t3-chrome-headless-shell && rm /etc/apparmor.d/t3-chrome-headless-shell`.
- **Durability:** the profile is on VPS3's root disk, which a VPS3 recreate wipes. It was set by hand, not through infra-vps `provision/vps3.sh`. After a recreate, rerun the setup command above.

**Why the tab now shows a plain Google sign-in rather than the Zenod one:** Zenod's sign-in `state` expires 10 minutes after "Continue with Google" is clicked (`exp` in the state token). A password typed hours later on that page would fail at Zenod's callback. So the tab was moved to Google's own sign-in (`accounts.google.com/ServiceLogin?continue=https://myaccount.google.com/`) for the same email. Once Jordi signs in there, the Google session stays in the T3 browser's default profile. On resume the agent clicks "Continue with Google" on cloud.zenod.dev, and Google passes straight through (with a one-time consent screen for a first sign-in).
