## Problem

The T0 drill (2026-10-31) paused the live Phylax container for ~5 min (23:17–23:22 UTC) while it tarred `phylax-data`. Testers will message at any hour.

## Change

`scripts/zenod-volume-backup.sh` defaults to **live mode** (`ZENOD_BACKUP_MODE=live`). The old behaviour is still there as `ZENOD_BACKUP_MODE=cold`. A disposable helper container (verifier image, `--network none`) runs the new `scripts/zenod-live-snapshot.mjs` in five steps:

1. **Live pass.** Every SQLite DB (detected by header) is copied with the `node:sqlite` online backup API in one step. That is one read transaction, so WAL writers keep committing. Every other file is copied into a staging dir under the archive dir. `-wal`/`-shm`/`-journal` sidecars are skipped, since each DB backup is self-contained.
2. **Live catch-up pass.** Re-copies the non-SQLite files changed since step 1 began.
3. **Paused pass.** `docker pause` holds only while a sync walk re-copies the non-SQLite files changed since step 2 began, plus a 2 s slack.
4. **Repair pass (after resume).** Re-copies any JSON in the snapshot that does not parse. A pause can freeze a writer halfway through a non-atomic rewrite. The stress test caught exactly this on `creds.json`, and the old cold pause had the same exposure.
5. **Archive and verify.** The staging copy is tarred, then checksum, isolated restore, verifier and health probe run as before. The staging copy is removed.

**Interface for T2.3:**

- Same three positional arguments.
- Output adds `mode=` and `paused_ms=` lines.
- `zenod-live-snapshot.mjs` must sit next to the script. `scripts/readiness-keeper/install.sh` now installs it, and `keeper.py` records `mode` and `pausedMs`.
- The verifier image needs Node ≥ 22.16 (`node:sqlite` backup). For Phylax, keep passing `ZENOD_VERIFY_IMAGE` = the Zenod image, as before.

What changed between iterations:

- **Run 1.** The paused pass re-copied 2554 files (30 s on network storage). `lutimes` rounds through float seconds, so half the copies were 1 ms off and looked changed.
- **Runs 2 and 3.** "Unchanged since before the previous pass" became the test, and a live catch-up pass was added. The public volume still paused 8 s because of async per-file stats and SQLite header reads on every changing sidecar.
- **Runs 4 and 5.** Sync fs calls, plus a SQLite list recorded by the live pass.

Run 1 is the data point that a pause of ~30 s already drops the WhatsApp socket. The old 5-minute pause was guaranteed to.

**Downtime of the receiver:** 725 ms frozen, 0 s disconnected. The process is frozen but its socket stays open, and no health probe failed.

**Delivered-message proof:** During the 725 ms freeze the WhatsApp WebSocket stayed open: no 408, no reconnect, the same generation, and `receivePath.status: ready` afterwards. Frames the server sends during a cgroup freeze queue in the kernel's TCP receive buffer and are processed on resume, so nothing is dropped. No end-to-end message was sent. No project-owned second WhatsApp number is configured for tests (pairing one needs a phone), and messaging anyone else is out of bounds. The rehearsal (EPIC-7 T5) exercises a real round trip.
