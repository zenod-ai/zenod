## How the 64 s was found

Production logs (container `f651a279`, VPS1 sudo allowlist, no content): the T7 account's vault holds 0 meaning pages and 1 log, yet each question (08:03:59, 08:06:08, 08:08:25Z) reached `[llm-cost] operation=tasking` 64 s later. Each question came more than 60 s (`readSyncTtl`) after the previous one, so every turn ran a full Drive pull first. The same account's `GET /api/vault` took 5.0 s and 13.3 s, and that request runs only part of a pull. Replaying a Drive vault on the repository's own `FakeDrive` gave these counts:

| past filings | pull downloads, main | pull downloads, #1656 (steady) | revision check downloads, main → #1656 |
|---|---|---|---|
| 2 | 40 | 4 | 8 → 2 |
| 8 | 82 | 4 | 14 → 2 |
| 16 | 138 (1.75 MB) | 4 | 22 → 2 |

What changed in `packages/core/src/vault/driveRepository.ts` (nothing it validates was dropped):
- The authority checks compare only ids and types, so they now list without downloading.
- A file whose Drive md5 equals the local copy is read locally.
- A committed journal unchanged since it was last validated (same id, md5, name, parent and properties) is skipped. Its check reads only its own file and content.
- A tombstone whose archived md5 already matched is not downloaded again.
- Folder listings run 8 at a time, keeping the old order.
- `pullForFiling` runs transaction recovery once.

A changed journal or file has a new md5 and is checked in full. An edit made in Drive is still imported (test).

Each saved note's journal is downloaded once by the first pull after the save, then never again. After a server restart that first pull costs what one pull costs now on main.
