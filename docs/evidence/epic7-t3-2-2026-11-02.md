# EPIC-7 T3.2: internal tokens exposed in the T3.1 window rotated (2026-11-02)

Run `run_88938702`. Bound epic: [EPIC-7](../EPIC-7-REAL-USER-TEST.md), row T3.2, under Jordi's answer to ask E7-A7 ("rotate now safely"). Trigger: the [T3.1 incident](epic7-t3-1-key-rotation-2026-11-01.md#incident-during-the-window), where a Dokploy `application.stop` response printed the full `zenod-mt` env into an agent session. This file holds names, counts and hash-equality booleans only. No value was printed during this run, and no API response body was printed (root L-5).

## Result in one paragraph

Agents could rotate four internal tokens and the Dokploy deploy-webhook token, and all five are now rotated. Every consumer was updated in one change: `zenod-mt` and the Phylax companion. Production was down for about 30 s, from 02:25:36 to 02:26:05 UTC (03:25 Madrid). The 3 live customer tenant-token envelopes were re-encrypted under the new `ACCOUNT_STATE_SECRET`, so no tenant lost its token. Health, readiness, Phylax (WhatsApp connected), the binding reconcile, tester-watch and the Google sign-in start all match the pre-change baseline. The old tokens are now refused. No Dokploy env in the fleet (29/29 scanned) and no config file on VPS1 or VPS3 still holds an old value. Six exposed third-party secrets can be rolled only from provider dashboards, so they stay with Jordi's ask E7-A10 ([list below](#left-for-jordi-ask-e7-a10)).

## What each secret does and who holds it (survey before the change)

| Secret | Consumers (by `secret find` same-value groups + VPS1/VPS3 file scan) | What a change breaks |
|---|---|---|
| `zenod-mt ACCOUNT_STATE_SECRET` | `zenod-mt` only (value unique in the fleet) | Customer session cookies (HMAC), OAuth/Drive/GitHub-app `state` signatures, **and** at-rest encryption of `customer-token-bindings.json` and `mcp-tokens.sqlite token_enc` (AES-256-GCM, key = sha256(secret)). Sessions and in-flight sign-ins are invalidated, so users sign in again (accepted). The at-rest data must be re-encrypted, or `ensure…` would silently mint new tenant tokens |
| `zenod-mt CONTROL_PLANE_TOKEN` | `zenod-mt` only. No VPS1 script, VPS3 config or other app holds it | Bearer for `zenod-mt` `/api/tenants*` control plane. Nothing scheduled calls it |
| `zenod-mt ZENOD_PHYLAX_CONTROL_TOKEN` | = `phylax CONTROL_PLANE_TOKEN` | Bearer `zenod-mt` → Phylax management (binding reconcile). Both sides must change together |
| `zenod-mt ZENOD_CHANNELS_PRIVATE_TOKEN` | = `phylax ZENOD_CHANNELS_PRIVATE_TOKEN` | Bearer `zenod-mt` → Phylax `/internal/zenod/channels/*`. Both sides must change together |
| Dokploy `zenod-mt` `refreshToken` | Nobody: the deploy poller uses the API, and no GitHub repo hook carries it (hash compare). The old hooks all point at the closed `dokploy.polyqu.com` | Only the `/api/deploy/<token>` webhook URL |

Bearer-only tokens (control plane, channels) are compared at request time and are not used to encrypt or sign anything stored. The only file hits for old values on VPS1 were env backups: the T3.1 rollback JSONs, `/root/.local/state/zenod-phylax-roll-20261101/{before,after-update}.json`, and this run's own backups.

## Side effects

- Every signed-in customer session (7-day cookie) became invalid at 02:26 UTC, so users sign in again. Any sign-in or connect flow open at that moment must be restarted. **This includes the T7 browser if it was parked on the Google password page:** reload `/auth/signin` (or `/auth/google/start`) before Jordi enters the password.
- About 30 s of downtime for `zenod-mt`. The Phylax container restarted once, and WhatsApp reconnected (`connected`).
