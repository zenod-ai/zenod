## What changed

- **Merge rule** `aggregate.merge_smoke()` (probe status × smoke result → row status), applied before transitions:

  | Probe | Smoke for this row | Row |
  |---|---|---|
  | grey | anything | grey (never alerted) |
  | any | none, no check for this row, or older than 45 min | probe status |
  | any | all pass | probe status |
  | green / amber / red | any check fails | **red**, problem = probe problem (if any) then `smoke check failed: <title>: <reason>`; test runs labelled |

  `probe.py` carries the latest smoke result in `raw.smoke` (`aggregate.smoke_summary()`); each component also gets
  `probe_status` and `smoke`. The page shows the problem under a red or amber row's status; last error source is
  `smoke: red`; the 7-day strip records the red sample through the existing `timeline.record(doc)`.
- **Same alerts as probe reds.** A smoke red changes the row status, so it reaches the S5 sender through the existing
  `alert_red()` under the same row key (`row-<n>`): one outage seen by probe and smoke is one transition, one alert.
- **Sender fix** (`scripts/watchdog/zenod-alert.sh`, #1493). The VPS1 watchdog shares row keys 1, 2, 4, 11, 12 with
  the page and cleared a key whenever its own check was green. With smoke reds that would have flapped
  (page ALERT → watchdog RECOVERED → page ALERT every few minutes). The sender now records which callers see a key red
  and sends RECOVERED only when none does; a caller silent for 30 min no longer holds a key. Pre-S4 state files keep
  the old behaviour.
- **Drill switch** for S6: optional `~/.config/zenod-health/smoke-drill.env` (`SMOKE_DRILL=--override …`) read by
  `zenod-smoke-prod.service`; documented in [SMOKE.md](../health/SMOKE.md).
