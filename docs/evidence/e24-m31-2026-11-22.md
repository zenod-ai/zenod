# EPIC-24 M31 evidence: the GitHub-vault tenant's saves and enrichments blocked since 22 Nov 02:21Z (2026-11-22)

Objective: Zenod: 5 testers: Jordi is tester zero; if his notes stop saving, nothing else matters. Content-free: counts, paths of machine files and hashes only; no note text was read or printed.

## Answer

The weekly tree sweep (Sunday 02:00 UTC window) was killed by the 02:20Z restart after it moved 379 filing receipts into `Archive/` and wrote pages, before its one commit. The 877 uncommitted paths made every save and enrichment fail with `filing_recovery_pending`, and the recovery could not replay a receipt that was gone. Fix live: recovery now keeps those changes on a side ref and returns the working tree to the published head. Nothing was deleted, reset or rewritten.


## Cause (production log of the `zenod-mt` container started 02:20Z, read-only `docker logs` form of `VAULT_LOG_CMD`)

- 02:21:28Z `[vault-recovery] writes blocked by filing_recovery_pending`: `conditions ["pending_receipt"]`, 377 receipts (9 Nov to 20 Nov), all `phase unreadable, where pending_change`, `otherPendingPaths 498`, `localHead == publishedRevision == fc3c5284` (the 01:40Z commit of `AlfaBlok/obsidian-brain`), `headPublished true`. So the clone had no unpublished commit; only an uncommitted working tree.
- The receipts exist in the published head (387 `Inbox/filing-*.md`), so "unreadable" meant removed from the working tree: exactly what `archiveReceipt` in `treeSweep.ts` does (copy to `Archive/`, check, remove the original), plus 121 page edits. 377 + 498 matches a sweep over every receipt past the age limit. `sweepTree` commits once at the end and only discards on a thrown error, so a killed process leaves the tree dirty. The sweep window opens 02:00Z on Sunday; the container was replaced at 02:20Z.
- Not the cause: the GitHub sign-in outage (the operator tenant uses the GitHub App, `mode=app`; no git error in the log), the M29 credential change, the old 9 Nov receipt (it was only the oldest of the pending ones).
- Why it never cleared: `recoverInterruptedFiling` requeues one `enrich_memory` job per receipt, but `enrichEvidenceFiling` finds no readable receipt for a changed tree and throws `filing_recovery_pending` again.
- Hit in the meantime: 2 `media_ingest` jobs (02:21:28Z, 02:21:57Z) and every `store`/`enrich_memory` since; all are durable jobs and were requeued by the recovery.

## Fix (PR [#1724](https://github.com/zenod-ai/zenod/pull/1724), `ci` green, merged `8079bd06`)

`VaultRepo.setAsidePendingChanges` + `engine.setAsideAbandonedChanges` + a step in `recoverInterruptedFiling`. Eligible only when the head is published, the only condition is `pending_receipt`, and every receipt is `unreadable`; it runs behind any live write under the vault lock. It stores all uncommitted changes (modified, deleted, untracked) as a stash commit and points `refs/zenod/set-aside/<time>-<sha>` at it, so neither a stash drop nor gc can lose it, then returns the working tree to HEAD. No commit, no push, no deleted note. Tests: `packages/server/test/vaultRecovery.test.ts` 6 of 6 (the killed-sweep case fails without the change; a replayable receipt, an unpublished head and a clean tree are left alone), `tsc` clean.

Production: staging ran `8079bd06` at 04:32Z; `scripts/promote-production.sh --sha 8079bd06` at 04:52:36Z (gate: demo 96/100/1.7, real notes in the run log); a later promote (`a4209aab`, M32) contains it.

## Learnings

- A restart inside the Sunday 02:00 to 06:00 UTC window can kill the tree sweep mid-run. The set-aside makes that harmless; the sweep for the week does not re-run (its job key exists), so receipts stay in `Inbox/` until the next Sunday: harmless, the receipts are intact.
- Requeued enrichments keep their old `created_at`, so a new save waits behind them (about 10 s each, 260 jobs). Not changed here; a store-first order is a possible follow-up.
- Gap: the launch-board totem has nothing to write back by hand (the board re-checks `cloud.vault-recovery`).
