# E24-M15 evidence, 2026-11-13: one memory read loaded every job Zenod ever ran

**Answer: each crash was one MCP read that parsed the account's whole task-job history onto the heap at once. That history only grows, so one call's live set grew with it until it passed Node's ~330 MB default. Fixed in this change: reads now load lean receipts only (163 MB → 19.5 MB held at 30,000 jobs). The image now also lets the heap use the 640 MiB container (`--max-old-space-size=448`). T7-F9 (3cba2ec5) did not touch this cause.**

```
 persona search (filter, no query) ─┐
 get_memory of one evidence ref ────┼─► recent(MAX_SAFE_INTEGER) ─► every job row, note text + receipt, JSON-parsed ─► +200 MB in seconds ─► exit 134
 subscriber notes API (2 routes) ───┘
                          after: captureReceipts() ─► finished store/media receipts, metadata only, text read per job only when the vault lacks it
```

| | before (production e0100de / 3cba2ec5) | after (this change) |
|---|---|---|
| what one filtered read loads | every task job of the account, any kind or status, note text and receipt JSON | finished `store` / `media_ingest` receipts: evidence ref, URL, revision, input metadata |
| heap held by that load, 15,000 jobs (62 MB JSON) | **81.5 MB** | **9.8 MB** |
| same, 30,000 jobs (124 MB JSON) | **163.0 MB** | **19.5 MB** |
| test (8,000 jobs, 4.5 KB each) | 43.9 MB | 2.1 MB |
| load loop, real vault copy + 15,000 jobs, 40 rounds: largest live set after a Mark-Compact | **259.4 MB** | **142.0 MB** |
| same loop, heap after forced GC between rounds | 91 → 97 MB | 90.9 → 97.1 MB (flat, the same small drift) |
| same loop at production's old ceiling (`--max-old-space-size=330`), 30,000 jobs | **FATAL ERROR: Reached heap limit** (the production message) | 20 rounds, 87.6 → 96.7 MB |
| heap ceiling in the image | Node default, ~330 MB (container 640 MiB unused) | 448 MB old space, 496 MB heap limit |

## What production showed

- Four crashes on zenod-mt, all V8 `Reached heap limit`, exit 134: 01:27:52Z, 01:32:24Z, 02:29:12Z and **06:41:49Z** (the fourth came after infra-vps's triage). The logs of crashes 3 and 4 survive. The log of crash 3 (container `61d83671`) ends `Mark-Compact (reduce) 316.8 (331.8) -> 316.7 (324.8) MB`. Crash 4 (`fc150d9a`) ends `318.9 -> 318.8 MB`.
- **The heap was not filling slowly.** VPS1's one-minute cgroup samples (`/var/log/vps-forensics`) show zenod-mt at 113 MiB anon at 06:41:02Z, 47 s before crash 4, and 157 MiB at 02:29:02Z, 10 s before crash 3. Each time about 200 MB was built inside one operation that still held all of it.
- **Each crash happened inside one MCP call.** Both surviving logs end with the operator account's `agent-team-console` client sending `initialize` and `notifications/initialized`, then a `tools/call` that never completed (02:29:10Z, 06:41:42Z). That is the console's team-services hub: personas call `search_memory` ("search at wake start") and `store_memory` through it. Traffic before crash 4 was light: 29 tool calls, about 20 saves and 4 web chats in 4 h 12 min.

## How it was found (no production data read beyond logs and counts)

1. A load harness in-process (`createZenodUnit`, a real HTTP server, the MCP tools, the task-job queue with a stand-in model, zero spend) on a synthetic vault and then on a local copy of the real vault (2,349 index rows, the same size production logs). MCP search, get_memory, memory_cloud and saves, with index refreshes after every save: the heap after GC stayed at 83 → 100 MB over 60 rounds. So **tier-0 index refreshes, store jobs and plain search are not the cause** (each was a suspect in the triage).
2. The Drive vault on the repository's `FakeDrive`: 30 pulls and revision checks with 20 filings held 41.4 → 42.2 MB on e0100de's Drive code and the same on 3cba2ec5. T7-F9 removed repeated downloads (speed), not retained data.
3. Every call shape the console sends, probed for peak heap: all small on an empty job history. The difference from production was the job table. `search_memory` with any filter or no query, `get_memory` of an evidence ref, and the subscriber notes API (`GET /notes?id=` and the note list) all called `recent(Number.MAX_SAFE_INTEGER)` (`memoryEntryCatalog.ts`, `mcp.ts`, `subscriberApi.ts`). Seeding the harness tenant with a production-sized history (store and enrich jobs, a real receipt shape of 1.9 KB, note text) reproduced the crash at the same message.
4. Production's own job count cannot be read without running the very call that crashes it, so it was not measured. The operator account adds hundreds of jobs a day (about 20 saves in the hour before crash 3 alone), and nothing ever prunes `task_jobs`.

## The fix (PR on `wt/m15`)

- `TaskJobStore.captureReceipts(evidenceRef?)`: one SQL read of finished `store` / `media_ingest` jobs. SQLite's `json_extract` pulls only the fields a memory entry reads from a receipt, so the note text and the rest of the receipt never reach the heap. With an evidence ref (get_memory, `GET /notes?id=`) it reads only that ref's receipts.
- `captureContent(id)`: the note text of one job, read only for an entry whose evidence is not in the vault yet. That is the only case where a receipt's text was ever used.
- `mergeMemoryEntries` takes that loader. All four callers use `captureReceiptsFor()`. The result is identical to the full history (test). Search pagination's `scannedReceiptJobs` now counts the receipts read, not every job (`zmrHistory.test.ts` updated: 653 → 2).
- Test `packages/server/test/captureReceiptsMemory.test.ts`: same merged entries as the full history (in-vault, not-in-vault, media digest receipts, older receipts, enrich and failed jobs, another tenant), a filtered search never calls `recent`, and the held heap at 8,000 jobs is under a sixth of the full load. All three fail on main and pass with the fix.
- Guard: `ENV NODE_OPTIONS=--max-old-space-size=448` in the Dockerfile's runtime stage, recorded in `docs/DEPLOYMENTS.md` with its rollback (delete the line). It reaches zenod-mt and zenod-staging only. ring, herald and zenod-cloud-test are idle on older pinned images, and Phylax has its own image. zenod-staging has a 512 MiB limit, so a full heap there would meet the container limit first; its load is light.

## Not changed

- Nothing on VPS1, no Dokploy env, no promote: the fix and guard ride staging from the merge and production from the next promote.
- The job table still keeps every job. Pruning old finished jobs is a separate, data-touching change that this fix does not need.
- Chat behaviour (root L-6): untouched.
