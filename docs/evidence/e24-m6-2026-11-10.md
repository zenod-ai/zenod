# E24-M6 evidence, 2026-11-10: releases no longer answer with an error

Row M6 of [EPIC-24](../zenod-errors-now-find-fix-and-monitor-so.md). Run run_ebd55a5d-4f20-45d1-b361-e5d4a17526ef.
Code: [#1587](https://github.com/zenod-ai/zenod/pull/1587) (`ceb7959`), [#1590](https://github.com/zenod-ai/zenod/pull/1590)
(`cb72902`), [#1591](https://github.com/zenod-ai/zenod/pull/1591) (`50af8a1`). How it works and how to undo it:
[DEPLOYMENTS.md, Zero-downtime rolls](../DEPLOYMENTS.md). Counts only, no request or message content.

**Bottom line: a release now starts the new Zenod beside the old one, moves traffic only once the new one is healthy, and
lets the old one finish what it is answering. Five real releases were measured this morning: 15,391 requests went through the front door in the
minutes around each swap, and none failed at a swap. Four releases had 0 failures in their window. The fifth had 3 POST
errors from a proxy keep-alive race that was not part of the swap; #1591 fixes it and is live since 08:12. The other errors
today came from two out-of-memory crashes during filing, which are M3's.**

## Before

M1 counted 13 failed requests across 3 releases on 9 and 10 November: Swarm stopped the old task first (`stop-first`,
no healthcheck), so every request in the 2 to 13 seconds until the new one listened got a 502.

## What changed

| When (UTC) | Change | Where |
|---|---|---|
| 06:03 | Swarm `start-first`, healthcheck on `/api/health` (5 s, start period 60 s), automatic rollback when the new task never turns healthy | Dokploy swarm settings of `zenod-mt` |
| 06:12 | stop grace 60 s and `ZENOD_STOP_GRACE_MS=60000`, so the old task may finish an answer that takes up to 57 s | Dokploy, env |
| 06:47 live | the app's shutdown budget follows `ZENOD_STOP_GRACE_MS`, and stores close only after the requests in flight are answered (before: a fixed 7 s cut, stores closed at once) | #1587 |
| 07:30 live | the image carries the same healthcheck, so clearing the Dokploy one cannot bring back an unchecked swap | #1590 |
| 08:12 live | Node keeps idle connections 95 s, longer than Traefik's 90 s, so a POST is never sent on a socket Node is closing | #1591 |

Why two copies at once is safe: the vault already has a cross-process write lock, jobs are claimed with leases, SQLite
runs WAL with a busy timeout; the WhatsApp session lives in the separate Phylax app, untouched by a Zenod release.

## Proof: a request loop during real releases

`scripts/release-probe.py` from VPS3 through Cloudflare and Traefik, about 10 requests a second on three paths:
`GET /api/health`, `GET zenod.dev/`, `POST /mcp` (expects 401). A failure is a network error, a timeout or a wrong
status. "Swap window" is 3 minutes either side of the moment health first showed the new version. Traefik column: every
request to the Zenod hosts in that window, people and Claude included, answered 5xx.

| Release | New version live | Probe, whole run | Probe, swap window | Traefik 5xx, swap window | Old task exit |
|---|---|---|---|---|---|
| trial, same image (redeploy) | 06:04:20 | 1,404, 0 failed | 1,404, 0 failed | 0 of 1,638 | cut one long answer at 7 s (exit 1): fixed by #1587 |
| ceb7959 (#1587) | 06:47:10 | 13,384, 0 failed | 3,149, 0 failed | 0 of 3,268 | exit 0 |
| 943e30d (E24-M3) | 07:10:54 | 12,679, 3 failed | 2,799, 3 failed | 3 of 3,080 | exit 0, 30 s drain |
| cb72902 (#1590) | 07:30:30 | 10,857, 181 failed | 3,203, 0 failed | 0 of 3,294 | exit 0, 30 s drain |
| f4dfbf3 (E24-M7) | 07:52:12 | 9,264, 0 failed | 3,131, 0 failed | 0 of 3,527 | exit 0 |
| 50af8a1 (#1591) | 08:12:08 | 11,093, 159 failed | 3,109, 0 failed | 0 of 3,214 | exit 0 |

After 50af8a1 went live, Traefik counted 0 errors in 1,437 Zenod requests up to 08:30.

The 3 failures at 943e30d were `POST /mcp` 502s at 07:09:34 (80 s before that release began), 07:12:26 and 07:13:12,
each while a filing held the event loop: Node had closed an idle keep-alive socket Traefik was reusing. A GET is retried
by Traefik, a POST is not. #1591 fixes it.

The 181 failures in the cb72902 run were all between 07:22:53 and 07:23:13, eight minutes before that release: the
943e30d task ran out of heap (`JavaScript heap out of memory`, exit 134) during filing and Swarm restarted it in 20 s.
That is M3's crash, not a release. The M2 alerts caught it: rows 1 and 2 red at 07:23:20, green at 07:26:45, row 13
red for 31 failed or stuck saves at 07:26:45. The 159 failures in the 50af8a1 run are the same kind: the f4dfbf3 task ran out
of heap at 08:07:37 (exit 134), 155 failures between 08:07:37 and 08:07:58, alert row 17 red at 08:08:12. One more POST
502 at 08:04:26 was the keep-alive race, on an image without #1591.
