Production truth · 25 August 2026

Zenod does not need another product.

It needs one final simplification: one WhatsApp number, one hidden channel service, and Zenod as the only agent behind it. The channel service is currently code-named Phylax; customers should never need to know that. Ring is separate and does not sit in this phone path.

Verdict: not ready for public beta today. The core memory system works, but the live WhatsApp route is split and 6 of the last 10 inbound messages were affected by a failure or misleading response. This is a finite stabilization problem, not a rebuild.

The approved product boundary

Zenod is the personal memory agent. It saves text, voice notes, images, and documents; it answers questions from that memory. It does not route to a council, execute code, manage a backlog, or impersonate other agents.

The internal channel service is the phone adapter. The current code name is Phylax. It owns WhatsApp connection, media download, transcription transport, retries, and delivery receipts. It is not a customer product and does not decide what the user meant.

Ring is not deleted. It remains available as a separate multi-agent product, but is not part of the Zenod WhatsApp number.

The one final code iteration

Package

Turn Phylax into an internal Zenod channel service

Keep the runtime code and container, but remove Phylax from public navigation, pricing, onboarding, customer settings, and copy. Move the simple sender-verification component into Zenod’s Channels screen. Keep only a protected operator health/session surface.

Provision

Make hosted checkout create the whole product

After a hosted subscription provisions the Zenod tenant, automatically mint a channel-scoped credential and register a private tenant binding. Apply fixed, versioned Zenod bindings. The customer never sees a downstream URL, bearer token, tool discovery, assistant URL, Ring ticket, or transcription-provider form.

Route

Make every channel reach Zenod directly

Text calls chat_with_zenod; voice calls store_memory; images/files call ingest_memory. Remove chat_with_ring from the Zenod product default and migration. Ring code and data remain intact for the separate Ring product.

Reliability

Land the eight audited remediations

Durable job/receipt state, no false timeout failure, bounded classifier fallback, failed-media retry, long-note segmentation, authoritative transcript audit, separate operation/delivery states, and no internal identifiers in customer replies.

Commerce

Implement one beta entitlement

Replace the current monthly/yearly-only offer with one hosted-beta monthly plan, managed model allowance, one verified WhatsApp sender, and visible usage/stop behavior. Keep paid signup fail-closed until the price and limits are explicitly approved and proved.

Proof

Ship one version-coherent release candidate

Build Zenod MT and the internal channel runtime from the same main commit, deploy immutable images, migrate the founder binding without resetting the WhatsApp session, run the full channel journey, then invite a small stranger cohort.

No destructive cleanup is required. Existing Phylax/Ring data, code, volumes, and histories stay in place. This iteration changes ownership, defaults, customer surfaces, and routing. Old routes can be retained as internal compatibility paths while Zenod tenants migrate.

Production and DevOps plan

Before deploy

Pin and protect

  • Back up Zenod and channel volumes, including WhatsApp session state.
  • Record current and target immutable image digests.
  • Prepare redacted config delta and tested rollback images.
  • Dry-run tenant binding migration; print IDs/status only, never secrets.
Deploy order

Memory first, channel second

  • Deploy the candidate Zenod MT image with direct memory tools.
  • Deploy the matching channel-runtime image.
  • Keep public signup closed.
  • Migrate only the founder tenant as canary; do not reset/re-pair the session.
Canary

Prove the actual phone

  • Text save and memory question.
  • Short and long voice note.
  • Image plus forced classification fallback and retry.
  • Restart during a pending job.
  • Audit transcript → Zenod job → outbound delivery.
Observe

One support timeline

  • Alert on session disconnect, inbound lag, job age, false terminal mismatch, retry/coalescing loss, and delivery failure.
  • Correlate by provider message ID and Zenod job ID.
  • Show channel health inside Zenod; keep deep diagnostics operator-only.
Rollback

Fail closed, never fall back to Ring

If the direct Zenod route fails, restore the previous immutable Zenod/channel images and bindings from the captured packet. Do not silently route Zenod customers back through Ring. Preserve queued jobs and session data; tell affected users capture is temporarily unavailable.

Scale

Cap beta, then replace transport

Start with a small named cohort on the existing shared number and no uptime SLA. Track queue/capacity and session incidents. Before uncapped availability, adopt the official Meta Cloud API transport behind the same internal interface and customer flow.

Failures observed in the last 48 hours

1

Ring invented a success reply

A normal business question received “Done — the change was verified,” unrelated property notes, and an internal test correlation ID.

Remediation

Remove Ring and its reply gate from this number. Send text directly to Zenod. Zenod’s phone persona is memory-only and may only save, retrieve, or clearly say a request is outside the memory product.

2

A retry produced a generic source error

Ring called duplicate memory-search tools, discarded a useful clarification, and returned “I couldn't read the connected source.”

Remediation

One Zenod turn, one memory operation at a time, one customer reply. No Ring tool selection, no duplicate dynamic peer calls, and no internal source language in the WhatsApp response.

3

Two saved memories were reported as failures

Zenod committed both memories, but Phylax’s outer request timed out around 62–64 seconds and told the user the operation failed.

Remediation

Use the existing durable Zenod job ID. Phylax acknowledges the capture, polls to a terminal result, and sends exactly one final receipt. A transport timeout must never overwrite a confirmed Zenod commit.

4

One image classification failed

The classifier returned empty, unparsable structured output. The transaction rolled back cleanly, but the image was not filed.

Remediation

Retry classification a small bounded number of times, then preserve the artifact in Inbox with an explicit “saved, filing pending” receipt. Classification uncertainty must not become data loss.

5

Resending the failed image did nothing

The resend was silently coalesced onto the already-failed canonical job, so it did not create a fresh attempt or reply.

Remediation

Coalesce only while the original job is processing or after it completed. A prior terminal failure must allow a fresh owner/job for a new provider message ID.

6

The audit tool looked in the wrong database

Ring reported no recent WhatsApp rows even though Phylax’s authoritative transcript store contained all ten interactions.

Remediation

Make Phylax the single authority for channel transcripts and expose that evidence directly to Zenod/support tooling. Do not substitute Ring’s empty local channel store.

7

The long voice note was only partly distilled

The raw 27,686-character transcript survived, but speech recognition mangled proper nouns and filing omitted a substantial product/sprint topic.

Remediation

Keep the raw transcript immutable, segment long notes by topic before filing, and retain uncertain named entities verbatim beside normalized candidates.

8

Operational statuses are misleading

A failure message can be successfully delivered while recorded as an outbound error, and the failed classifier call can disappear from a “complete” model timeline.

Remediation

Record operation status and message-delivery status separately. Log failed model calls as first-class attempts so support can reconstruct the exact turn.

What the confusing “typed terminal mutation” sentence means

It is a programming safety rule, not a new product or a Ring concept.

Plain English: when Zenod tries to save something, it must eventually return one machine-readable result tied to that exact message: saved, failed, or still processing. The channel service may say “saved” only when the matching Zenod result says saved. If the user only asked a question, the system must preserve the answer and must not transform it into a fake “change verified” message.

This would have prevented the two worst symptoms: a real save being reported as failed, and a read-only answer being rewritten as an invented success.

The final stabilization iteration

P0 · route

Bind Zenod’s number directly to Zenod

Change the live text binding from chat_with_ring to chat_with_zenod on the existing Zenod downstream. Preserve Ring and every other product route. Pin a regression so new Zenod tenants cannot silently inherit the legacy Ring text default.

P0 · receipts

Make capture completion durable

Use Zenod job IDs end-to-end, wait asynchronously, and send one terminal WhatsApp receipt. Eliminate the nested synchronous timeout that currently lies about successful commits.

P1 · recovery

Make failures recoverable

Inbox fallback for classification failure; fresh attempt after a failed canonical media job; visible pending/error receipt; no silent coalescing.

P1 · fidelity

Harden long voice notes and audit

Topic segmentation, verbatim entity preservation, authoritative Phylax transcript reads, and separate operation/delivery timelines.

Acceptance

Prove one small real journey on exact deployed SHAs

Text save, text memory question, short voice, long voice, image, failed-image retry, restart/timeout recovery, and transcript audit. Every case gets exactly one truthful terminal reply, and no Ring tool/correlation language appears.

Release acceptance checklist

  • One WhatsApp number resolves to one Zenod tenant and one Zenod MCP connection.
  • Text never calls chat_with_ring for the Zenod product.
  • Voice, text, and media each create at most one Zenod operation per provider message.
  • Every accepted capture survives restart and ends with one truthful terminal receipt.
  • A failed prior image job can be retried with a new message.
  • Long-note raw evidence is complete even if classification is uncertain.
  • Support can retrieve the exact internal channel transcript and correlate it to the Zenod job and WhatsApp delivery.
  • No response exposes Ring, MCP tool names, correlation IDs, or internal source errors.
  • Ring functionality remains intact on its own surface.
  • Production deployment uses an approved immutable image, target, redacted config delta, and rollback plan.
