## What runs

- VPS3 user timer `zenod-promote-tick.timer`: hourly at :41, up to 2 min random delay, off the quarter hours. It was installed by `scripts/promote-schedule/install.sh`; `install.sh --remove` takes it out.
- The service fetches `origin/main` and runs `scripts/promote-schedule/tick.py` from there, as the memory-tests timer does, so a merged change is used on the next tick. A tick runs `scripts/promote-production.sh --sha <staging sha>` (root D28 gate, promote and rollback, all unchanged) only when every rule passes, checked in this order:
  `locked` → `vps1-unreachable` → `staging-down` → `production-unreadable` → `nothing-new` → `quiet-hours` (22:00-08:00 Europe/Madrid, unless production's health is not ok or the Delivery Manager touched `~/zenod-eval/promote-now`) → `paused` (zenod-mt not in `promote_targets` of VPS1 `hosts/vps1/deploy-poller.json`, read over ssh on every tick) → `batching` (staging must have run the sha for 30 min, using VPS1's roll time) → `hourly-limit` (no promote, rollback or gate run in the last 60 min) → `gate-failed-earlier` (6 h).
- Each tick writes one line to VPS3 `~/zenod-eval/promote-schedule.jsonl`. When the gate fails, production is not moved and nothing is sent to Jordi. The first failure for a sha leaves one desk note for the Delivery Manager in this repo. M11's gate work is not touched: the tick runs whatever `promote-production.sh` is on main.
- Manual promotes take the same lock: `flock -n ~/zenod-eval/promote.lock scripts/promote-production.sh` (docs/DEPLOYMENTS.md "Staging and promote").
