## Why it was slow

M1 saw one search take 0.4 seconds and another 4 seconds on the same index, after notes were filed. Three things added up:

1. **The memory tree was rebuilt from scratch on every search.** Each hit carries its place in the memory tree. To work that out, every search read and parsed all of the vault's ~700 pages one at a time. On VPS3 that alone took about 0.8 seconds per search, and more on production.
2. **The index re-read the vault inside the first search after a filing.** A filing marks the index out of date, and the next search did the whole refresh itself (changed files, tree places, links), then rebuilt its caches.
3. **Once a minute a search waits for a pull from GitHub.** On production that took about 1.7 seconds: a search that spent 346 ms in the index took 2,053 ms in total (05:51:08 UTC today).

## What changed

- **The tree is kept while the vault is unchanged.** It is rebuilt only when a Markdown file is added, removed or changed. A file counts as changed when its path, modification time or size differs. A file changed in the last 100 ms is never trusted, the way Git handles files changed within one clock tick. When the tree is rebuilt, pages are read 16 at a time instead of one by one, in the same order as before.
- **The index refreshes in the background right after a filing.** 250 ms after a write it re-reads the changed files and rebuilds its caches and the tree, so the next search usually finds everything ready.
- **A search during a refresh waits for it.** Before, a search arriving mid-refresh could read the rows from before the filing and miss the new note. This was an existing race; a new test fails without the fix. A write that lands while a refresh is reading also keeps the index marked out of date.
- **The search log line now shows the whole call's time** (`tool N ms`), next to the index time it already showed.

**Tried and dropped:** letting a search answer from the local copy while the GitHub pull runs behind it. CI caught that this breaks two promises: a search must see pages pushed from elsewhere, and on Google Drive vaults a read during the pull fails with "filing in progress". So the pull still runs first, once a minute at most. A search more than a minute after the previous one still waits for it, about 1.7 seconds on production. Changing that trades freshness for speed and needs its own decision.

### What this shows

1. **Filing no longer slows search.** The refresh after a filing costs 0 to 214 ms. Before the fix, the search did the whole refresh itself and the index part took up to 4.5 s.
2. **The cold case is gone.** The first search after the 04:19Z restart (04:38Z) spent 361 ms in the index, with refresh 0. The 08:44Z search on 10 Nov had spent 4,733 ms.
3. **The GitHub pull is now the largest part.** Without the pull a whole call takes 288 ms, and with it 1.9 s. 20 of 23 real searches came more than a minute after the previous one, so almost every search Jordi makes waits for the pull. The fix for this is the "searches more than a minute apart" follow-up. It reads the pull in the background, which is a freshness decision that is Jordi's to make.
4. **The index part is slower on production than in the lab.** It took a median of 540 ms here, against 80 ms on the vault copy on VPS3, with 1,900 rows now against 1,428 in the lab. VPS1 is overloaded: load average 6 to 7 on 4 cores at 02:34Z, the reason promotes are paused (infra-vps/EPIC-2-A50).
