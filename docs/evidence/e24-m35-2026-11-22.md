# EPIC-24 M35 evidence: production killed as unhealthy three times, and a stop that outran Swarm's grace (2026-11-22)

Objective: Zenod: Get 5 testers: a production that restarts under testers drops their replies. Run run_6c2745bc-37d3-4ce1-821a-6b054727dd7a. Content-free: timings and code paths only.

## Answer

**The index no longer holds the event loop in one block, and a stopping task hands its filing jobs back at 53 s instead of running past Swarm's 60 s grace. Merged in PR [#1747](https://github.com/zenod-ai/zenod/pull/1747) (`ci` green); the live measure is at the end.**

```
              before (crash logs, 20:29-20:42Z)          after (this change)
 write        one block 1.0-2.9 s                        ~20 ms slices, loop runs between
 warm         one block 1.0-1.7 s (four builds)          four slices
 search       one block 1.1-1.5 s (8+ statements)        a slice per statement
 stop         AI filing runs past 57 s, dockerd kills    no new job from SIGTERM; running filing
              at 60 s (exit 137)                         handed back at 53 s; stores close at ~54 s
```

## What the crash logs showed

Two containers' last minutes, saved by infra-vps on VPS1 (`~/.local/share/infra-vps/crash-logs/`, read-only): `[memory-index] sync section held the loop` 1.0-2.9 s in `write`, `warm` and `search` every few seconds; `event_loop.blocked` 5.7-45 s in `captureReceipts` (fixed in #1739, live before this change); the second container's last line is `shutdown exceeded 57 seconds; closing remaining HTTP connections`. The 02:19Z kill (a core pinned for 15 min) has no log; the watchdog from M34 is what named these.

## Fix 1: the memory index in slices (packages/core/src/vault/memoryIndex.ts)

- The write is one SQLite transaction, still one commit; between about 20 ms slices it hands the loop back (`setImmediate`). Lineage resolution and relineage, which only awaited microtasks, now yield too; the weighted-link rebuild yields between its edge loop and its inserts.
- The warm-up builds its four caches one slice each. A search (and `ownNotes`, `askedNotes`, `matchFor`) yields between its full-text statements: each query word is two statements of 60-190 ms on a 4,500-row test vault.
- A gate keeps results as before: a read waits for a write in progress, a write waits for reads in progress. No search sees a half-written index.
- Not changed: the statements themselves (a single statement is still one block, 190 ms at most on the test vault; on VPS1 about 2.5 times that). A worker thread would remove even that and is its own row if the next measure still shows blocks.

Measured on a synthetic vault of 4,561 rows (VPS3, load about 12): write 3.3 s as one block, now slices of about 20 ms; one search 840 ms as one block, now slices of at most 190 ms.

## Fix 2: shutdown inside the grace (packages/server)

- At SIGTERM `stopTakingJobs()`: no queue claims another job. A save arriving while HTTP drains is still accepted (durable) and waits for the replacement.
- At 53 s (4 s before the 57 s force close, under Swarm's 60 s) `handBackRunningJobs()`: each running `store`, `media_ingest` and `enrich_memory` job goes back to `queued` with its claim cleared and its retry count untouched. A late result from the old AI call is ignored (the claim is gone), and its next fence throws `task_job_claim_lost`.
- The queue stops waiting for the drains one second after the hand-back, so stores close at about 54 s, before the 57 s deadline. A job that finishes by itself earlier costs nothing.
- The replacement polls for queued jobs every 60 s (`resumeAtStart`), so a job handed back by a task that is stopping runs again within a minute.
- Chat, task and desk jobs are not handed back: running them twice is not safe. They still get the whole grace.
