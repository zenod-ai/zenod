Simple definition: “Included Phylax” means the host product provisions one internal channel tenant and renders the shared channel controls inside its own UI. It does not mean duplicating a Phylax subscription, merging databases, moving credentials, or sharing application code paths.
The simplest Phylax: WhatsApp ↔ Phylax ↔ one downstream service. Inbound, Phylax is an MCP client calling that service. Outbound, Phylax is an MCP server exposing send_message and delivery status. With a one-to-one binding it is effectively that service's WhatsApp extension, while still retaining its own process, session, journal and failure boundary. Multi-tenant hosting is many isolated one-to-one bindings on one Phylax runtime—not a new intelligent router.
Integrated authentication

Provisioned, tenant-scoped MCP binding

  • The customer signs into Zenod or PM once.
  • The host backend provisions a durable Phylax↔service binding.
  • No internal URL or token is pasted into the product UI.
  • Deploys never rotate or invalidate the binding credential.
Native Phylax authentication

MCP OAuth, with bearer fallback

  • The customer enters the downstream MCP URL.
  • Phylax completes MCP OAuth when the server supports it.
  • A manually supplied bearer token remains the simple fallback.
  • The resulting credential is encrypted and belongs to that tenant.
One media contract: every adapter receives the same bounded envelope—provider message ID, sender, reply context, media type, raw artifact reference, duration, transcript when ≤2 hours, explicit archive_only when over 2 hours, and a stable idempotency key. The downstream returns one canonical terminal result; Phylax turns it into one channel receipt.
MCP is also the UI seam: Product UI → authenticated product backend → Phylax MCP. The thin host facade authorizes the signed-in tenant and calls the same typed tools used everywhere else: channel_status, start_verification, test_delivery, disconnect_channel and send_message. The browser never holds the private Phylax credential. The Phylax standalone UI uses the same service operations, so there is one control contract rather than parallel native APIs.

What happens when a customer subscribes

One customer account; one internal channel binding.

1 · Host product

Create tenant

Zenod or PM creates its normal customer/account and remains the billing authority.

2 · Host backend

Provision channel binding

Call Phylax MCP with a stable external tenant reference and the named adapter kind.

3 · Customer UI

Verify identity

The customer opens Channels and proves their WhatsApp or Telegram identity.

4 · Ongoing

Proxy control

The signed-in UI calls its own backend; that backend invokes Phylax for status and actions.

Terminology: the host provisions a Phylax channel tenant/binding, not a duplicate customer user. The customer never receives a second login or second subscription.

04 · Responsibility map

Who owns what—permanently

Most prior instability came from changing ownership while changing presentation. This contract freezes ownership so UI work cannot silently move credentials, sessions, transcription, storage, or business logic.

Phylax owns

  • WhatsApp/Baileys and Telegram transport
  • Shared session and sender verification
  • Provider message journal and dedupe
  • Raw media staging and ≤2h transcription
  • Retry, delivery and provider receipt

Zenod owns

  • Tenant identity, memory and MCP surface
  • GitHub vault and search/citations
  • That tenant's Google Drive connection
  • Raw audio archive and archive receipt
  • Memory classification, commit and pointer entries

PM owns

  • Project and proposal state
  • Proposal URLs and revisions
  • Reply-to-proposal correlation
  • Acceptance/rejection authority
  • PM-specific conversation policy

Zenod voice-note lifecycle

Storage receipt is an application receipt, not a transport guess.

1 · Phylax

Capture first

Journal provider ID and raw bytes before optional processing.

2 · Phylax

Transcribe ≤2h

Never ask for a 30-minute confirmation. Over 2h is marked “archive only.”

3 · Zenod

Archive + commit

Upload actual audio to that tenant's Drive and create the memory or pointer entry.

4 · Phylax

Deliver truth

One final receipt includes memory path and Drive archive outcome.

01

Deploying code never rotates customer tokens. Rotation and revocation are explicit, named, confirmed operations.

02

Credentials stay with their tenant and owning service. No global Google credential can replace a tenant's Drive authority.

03

Optional accounting cannot block capture. Raw evidence is journaled before usage reporting or classification.

04

Rolling deploys are additive and schema-safe. New optional metadata is omitted when the older peer cannot validate it.

05

One provider message, one durable job, one terminal receipt. Concurrent voice notes have distinct stable keys.

06

Phylax adapters are named and bounded. No generic router silently changes Zenod or PM behavior.

07

Bundling does not duplicate customers. Host product billing is authoritative; Phylax gets only an internal tenant binding.

08

Public UI never exposes internal service credentials. Integrated control calls use a private tenant-scoped backend boundary.

05 · Commercial metering

One plan. Separate cost ledgers.

Phylax creates real costs and must account for them where they occur. The host product owns the customer relationship and allocates part of the bundled allowance to the customer's Phylax channel tenant.

No double counting and no second customer subscription.

The clean accounting rule: Zenod does not copy Phylax usage into the Zenod ledger as if Zenod incurred it. Each service keeps its authoritative append-only usage events. The host product computes the customer-level projection and P&L from both ledgers, and can transfer more internal allowance to Phylax through an idempotent, audited grant.

One Phylax core, interchangeable allowance issuers

Standalone is an extension of the same system—not a later rebuild.

Allowance issuer A · integrated

Zenod or PM billing adapter

  • Receives the host subscription event.
  • Maps the host customer to the existing Phylax channel tenant.
  • Calls the same idempotent grant_allowance operation.
  • Shows the combined plan projection in the host UI.
Allowance issuer B · standalone

Phylax billing adapter

  • Receives the native Phylax subscription event.
  • Maps it to the existing Phylax channel tenant.
  • Calls the same idempotent grant_allowance operation.
  • Shows the same metering projection in the Phylax portal.
Shared core below both issuers: one tenant schema, one allowance-grant ledger, one usage-event ledger, one admission/enforcement path, one MCP control surface, one channel settings model, one delivery journal and one reusable UI component set. The tenant records only an explicit commercial_owner = zenod | pm | phylax and the external plan-period reference; it does not select a different runtime.
Capture remains safer than accounting: Phylax journals raw evidence before optional metering writes. Allowance is checked before starting a paid transcription/delivery operation, but a temporary ledger-reporting failure must never lose already received media. Provider truth, deterministic estimates and unavailable cost data remain explicitly distinguishable.
06 · Scaling vision

Scale the seam, not the coupling

Every new product gets a small adapter and UI composition. It does not fork the transport, copy the vault, or invent a new authentication system.

Tenant routing record

  • channel_tenant_id
  • host_product = zenod | pm | standalone
  • adapter_kind + opaque destination reference
  • verified identities and media policy
  • no customer plaintext internal tokens

Durable processing

  • Partition work by tenant and provider message ID
  • Lease journal entries for horizontal workers
  • Persist terminal result before delivery
  • Replay delivery without replaying application mutation
  • Keep channel and application volumes independently backed up

Product expansion

  • Zenod adapter: fixed, direct memory contract
  • PM adapter: proposals + optional Zenod retrieval
  • Standalone adapter: customer-configured MCP/webhook
  • Future Meta Cloud API behind the same Phylax seam

Release discipline

  • Versioned adapter contracts
  • Consumer-first compatibility for new required behavior
  • No credential migration as a side effect of startup
  • Exact two-service candidate and rollback proof
  • Live smoke per product adapter
07 · What lands now

Clarify broadly. Implement narrowly.

Yes, this contract should land before the final public-beta rollout resumes. No, the current refactor should not expand into building the PM adapter or a redesigned standalone Phylax business.

Public-beta implementation slice

  • Preserve the current two services, sessions, volumes and tenant credentials.
  • Ship the direct Zenod adapter for text, voice and media.
  • Expose tenant-safe WhatsApp/Telegram controls only inside Zenod Hosted.
  • Build Phylax metering once with an issuer-neutral grant ledger; connect the Zenod allowance issuer first.
  • Make concurrent voice capture durable and Drive archive receipts truthful.
  • Freeze authentication: deploys cannot rotate or invalidate MCP clients.
  • Deploy one version-coherent image, then run overlapping-voice, Drive and MCP acceptance.

Explicitly not in this refactor

  • No merging Zenod and Phylax runtimes.
  • No moving STT or WhatsApp sessions into Zenod.
  • No PM proposal logic inside Phylax.
  • No new universal routing framework.
  • No Phylax-only commercial rebuild before Zenod beta.
  • No acceptance of the pending sprint proposal from this artifact.
Recommended sequencing: stabilize and release the Zenod Hosted adapter first. Then land the Phylax standalone UI against the same channel API. Then build PM-over-WhatsApp as a PM adapter, using Phylax for transport and Zenod MCP for cited memory. This keeps the pending PH1–PH4 direction aligned without making it part of the current beta critical path.
Open commercial choices—deferred, not architectural blockers: whether standalone Phylax has its own price; whether PM bundles Zenod memory or links an existing Zenod entitlement; and whether self-hosted Zenod later supports a separately operated Phylax add-on. The service boundaries above remain valid under any of those choices.
