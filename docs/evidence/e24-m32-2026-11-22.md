## …6839: linked, flagged twice by a race in our check

| Time (22 Nov) | What the check read | Why |

| 01:11Z | linked | binding active, WhatsApp verified |
| 01:26Z | "channel still being set up, our bug" | the tick landed inside the 5-minute Phylax refresh (see below); the desk note then failed to push (GitHub sign-in revoked) |

| 03:41Z | back to each tester's true step | |
| 04:05Z to 04:22Z | 151 reads every 4 s: …6839 `active`/`linked` every time | |

Why: every 5 minutes `bootstrapAccounts` called `recordEntitlement` for every account, which wrote `state='setting_up'` (and cleared the error) before the remote reconcile put it back to `active`. A read in between returned "setting up", and a Settings or code request in the same instant got 503 `channels_unavailable`. The window is short: 151 live reads over 14 minutes did not catch it, so this is the cause read from the code and the two :26 timings, not a window seen live. Phylax and the tenant log write no line for a binding state change, so the log cannot show it.

His WhatsApp itself was never lost: tester-watch shows the phone `verified` and the binding `active` at 04:05Z, the link is the 21 Nov 06:05Z one (M30), and no inbound message from him reached Phylax since.

**Would a message from him be saved now?** Read as far as it can be without a message in his name: binding `active`, phone `verified`, tenant mapped, 0 failed captures. The same path saved Jordi's 21 Nov 16:18Z voice note. His first note is the real proof (E7-S18 and E26-S3 watch for it).
