## What the page shows

A new column **Last 7 days, UTC** next to each component name (the colour column stays). Per row, one SVG strip,
2 px per hour, 168 hours, day ticks in the header:

- **Status band** (top): the worst status in each hour. Solid colour = this page's own probe; lighter colour =
  rebuilt from a log that states it (rule per row below); hatched = no history. Hovering a band shows its span.
- **Key number** (below): bars for counts per hour, a line for durations and levels; hatched where the source's
  history has not started; an hour inside the history with no event is drawn empty or as zero, never invented.
- A caption: the number now and its 7-day max, and where each part of the history comes from and since when.

## Data (VPS3, `~/.local/state/zenod-health/`, 0600, counts, durations, statuses and timestamps only)

- `samples.json`, written by `probe.py` every 5 min (hook `timeline.record(doc)`): each component's status per run,
  kept at 5-min resolution for 24 h and rolled up to the worst status per hour for 8 days.
- `hours.json`, written by [`timeline.py collect`](../health/s1-live/timeline.py) (new user timer
  `epic6-s1-timeline.timer`, every 15 min, last 3 hours recomputed): one bucket per component and hour. It runs the
  same file on VPS1 as `python3 - --remote-hours SINCE` with the probe's existing narrow sudo rules (Traefik access
  log `cat`, `docker ps/inspect/logs --timestamps`, `journalctl`) plus the S5 alert log in t3agent's home. No new
  access, no message text, no ids, no keys. An hour a source only partly covers (log reset by a redeploy) keeps the
  fuller value.
- Backfill, run once at 16:44 UTC (`timeline.py backfill`): 7 days of the VPS1 sources below, plus 1,776 status
  samples from the probe service's own VPS3 journal (one `{component: status}` line per run since the page went live).
