## 1. Why call_7415c108 wrote nothing

- `get_task_result` for job `f1e02e14-2fb3-412a-bd6d-d348e9099cc9` on Zenod production (Jordi's tenant, read
  through the console's Zenod connection, 04:4xZ) returns status **error**:
  `error: could not lock config file .git/config: File exists`.
- `search_memory sourceId=call_7415c108`: 0 entries in 1328 scanned. Nothing was written, so a retry cannot double it.
- The container that ran the job (01:24:59Z) was replaced by the 02:29Z, 02:48Z, 03:51Z, 04:03Z and 04:20Z rolls;
  its stdout is gone (swarm keeps 5 old tasks), so the line above is the only trace.
- **Cause:** the vault clone's `.git/config` is rewritten on every remote operation (`remote set-url` with a fresh
  token in `VaultRepo.ensureFreshRemote`, `addConfig` in `VaultRepo.open`). During agent_team's back-fill burst
  (31 calls, 01:25–01:40Z) two git calls on the clone wrote it at the same moment and one lost the `config.lock` race.
  The job then ended `error`.
- **Second defect:** `TaskJobStore.enqueue` returns the existing row for an idempotencyKey whatever its state, so a
  resend under the same key got the dead `error` receipt forever (what agent_team saw).

## 2. Fix (PR [#1628](https://github.com/zenod-ai/zenod/pull/1628), deploy gate, self-merged when `ci` is green)

- `packages/core/src/git/vaultRepo.ts`: `retryConfigLock` retries a `could not lock config file` error up to 5 times
  (150 ms × attempt); the write is idempotent.
- `packages/server/src/taskJobStore.ts`: a `store` job with a `sourceId` that ended `error` or `interrupted` is
  queued again when resent under the same idempotencyKey. Capture looks up the sourceId before appending
  (`captureEvidence`), so the Log entry is still written once. Done jobs and jobs without a sourceId are unchanged.
- Tests: `packages/core/test/vaultRepoConfigLock.test.ts` (new), `packages/server/test/taskJobStore.test.ts`
  (28 pass, one new case).
- Production moves only on the Delivery Manager's promote (root D28), paused on VPS1 since 2026-11-11 (infra-vps desk
  note 675e4c02). Until it runs, a same-key resend still returns the old error receipt.
