# T7-F3: no billed answer is thrown away on a busy vault (2026-11-12)

Row: T7-F3 in [EPIC-7](../EPIC-7-REAL-USER-TEST.md), from [T7 round 5](epic7-t7-r5-2026-11-12.md) R5-F1. Run: run_2f8202cb-9c45-443c-8da1-57c80cfb9915. PR [#1644](https://github.com/zenod-ai/zenod/pull/1644), merged as `c5164904` after `ci` passed (14 min 29 s).

**Bottom line.** The cause was not a filing. Each memory read checks the vault's revision under the vault lock, with a wait of 0 ms. When 2 or 3 answers ran at once, their checks collided, or one collided with another answer's read-sync pull, and each collision looked like "filing in progress". Each paid answer was then replaced by the retry line. A single chat never collides, which is why single chats answered. The fix makes concurrent answers share one check and lets a check wait up to 3 s for a short holder. A memory question (`ask`, `ask_brain`) on a vault that a real filing holds now gets the same retry line **before** the model call, so nothing is billed. Chat replies are unchanged (root L-6).

## Cause, in the code

- `packages/core/src/engine/engine.ts` `safeReadRevision()` ran `withVaultWriteLock(vaultPath, …, 0)`. The lock is a SQLite `BEGIN IMMEDIATE` on a private file, so two probes from two answers in the same process exclude each other, and a 0 ms wait turns a few milliseconds of overlap into `VaultWriteBusyError`.
- `syncForRead()` also takes the same lock for its pull from origin, which can take seconds on a Drive vault.
- Any busy probe set `readBusy`, and `finalize` returned "Memory filing is in progress. Please retry your question shortly." after `llm.answer` had already been paid for.

## Fix (smallest safe change, engine freeze: breakage only)

| Change | Why it is safe |
|---|---|
| One in-flight revision probe per engine, shared by every concurrent answer | A probe joined while it holds the lock reads the current revision: no writer can commit until it releases. The per-turn probe already shared this way |
| The probe waits up to 3 s (`readLockWaitMs`, default 3000) for a short holder | A long filing still turns the read away as before. The read is never blocked behind filing for minutes (#96 stays fixed) |
| `ask` checks the vault before `llm.answer`; if a filing holds it, the retry line comes back with no model call | Same text as before, only earlier. `ask` is always a memory question, so its answer would have been discarded anyway |
| A turn that met a busy vault fails its later reads at once | No repeated 3 s waits inside one turn |
| No change to `chat` | A chat may be a capture ("keep a note"), which must work during filing. Chat keeps its old reply on a real filing (L-6) |

Not covered, by design: a chat (or an `ask` whose vault becomes busy after its first check) that meets a real long filing mid-answer still pays for one model turn and returns the retry line. Before the fix this happened to every parallel answer even with no filing. After it, it needs a real filing that starts during the answer.
