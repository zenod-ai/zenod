## 23:11Z in detail (the one with logs)

The container log of the current `zenod-mt` task (`docker logs --since 23:10 --until 23:14`) has nothing between 23:11:23.26 and 23:12:04.97, then:

```
23:12:04.971 POST /mcp 200 duration_ms 41641.85  mcp.methods ["tools/call"]  (client agent-team-console)
```

Traefik's access log shows every request that arrived in that window waiting for the same release (origin duration = wait):

```
23:11:23 cloud.zenod.dev /mcp           499  14976 ms
23:11:25 zenod.dev /                    499   9873 ms   (client gave up)
23:11:40 zenod.dev /connect             499  14860 ms
23:11:54 zenod.dev /, /connect, /pricing, /api/health   200  10.8-11.0 s   (answered 23:12:05)
23:11:55 cloud.zenod.dev /api/health    499   9910 ms   (the watchdog, curl -m 10)
23:12:12 zenod.dev /                    200      5 ms   (normal again)
```

13 requests over 3 s in that minute, none in the minute before or after. The watchdog's `fetch` makes two 10 s attempts 5 s apart, so a 40 s stall gives `000`.

What was calm: VPS1 data volume (`sar -d` sdb 23:10-23:14: await 1.5-1.8 ms, 16-27% util, no freeze), host load 2-3, `zenod-mt` cgroup at 8% CPU before and 53% during the call, no swap, no crash (container healthy, no task restarts). The container's page cache grew from 48 MB to 264 MB in that minute (`/var/log/vps-forensics`), so the call was reading a cold index and vault.

Why one call stops everything: Zenod searches memory with a synchronous SQLite index (`node:sqlite` `DatabaseSync`), so a long search blocks the one event loop that also serves zenod.dev. A normal warm search already costs 3.2 s of index time on 3,578 rows (23:32:05Z, `[memory-search] tier-0 index, 3178.8 ms`). The `agent-team-console` calls `search_memory` for every team wake. The call at 23:11 did not log a `[memory-search]` line (that line only prints when a search has hits), and the request log did not name the tool, so which search it was is not proven.

Why "recovered 23:26:41Z": the watchdog itself was green at 23:13:38Z. The page's own smoke claim kept the row red; `za_clear` releases a row only when every caller has cleared it or 30 min have passed without a red from one of them.

Also seen, not this row: `[quick-index] update failed: Drive transaction journal 9172c14c-… has a preserved external edit` every 5 min since the 22:56 boot, and `[vault-recovery] UNRESOLVED` at 23:27Z. One tenant's Drive vault needs recovery. Noted for the Delivery Manager.

## Fix

| Part | Change | Where |
|---|---|---|
| Blip does not page | row-1 and row-2 alert on a second red sighting at least 120 s after the first (watchdog every ~2.5 min, page probe every 5 min). A green in between deletes the held sighting. | Real outage still pages | still red at the second sighting: normal ALERT, 30-min re-alert, one RECOVERED | same |
| Next stall names its tool | the `/mcp` request line carries `mcp.tools` (names only, never arguments) | `packages/mcp-chassis/src/index.ts` |
| One long block is seen | `event_loop.lag` also fires when one block reaches 5 s (`EVENT_LOOP_MAX_WARN_MS`); p99 over 60 s and utilization missed a 41 s block | `packages/server/src/eventLoopHealth.ts` |

Tests: `bash scripts/watchdog/watchdog-logic.test.sh` ALL PASS (84 checks; new ones cover the 23:11Z case, the 21:41Z page-probe case, a real outage and keys that stay unheld). A dry run of the whole watchdog against dead URLs queued nothing for row-1 and row-2 on run 1 and alerted both on run 2 (150 s later), while row-4 and row-11 alerted on run 1. Vitest `eventLoopHealth` (5) and `logging` (2), `tsc --noEmit`.

## Not fixed here

The real cause, a synchronous search that can hold the whole app for tens of seconds under a cold cache, stays. Moving the memory index query off the main thread is a bigger change to the tester-facing app than an alarm row should carry. Follow-up proposed on the row (M25): after the next stall shows the tool name in the log, run the index search in a worker thread or bound its blocking time. VPS1 host: nothing to hand to infra-vps, the disk and CPU were calm at 23:11Z; the data-volume freezes of M21 are a separate cause.
