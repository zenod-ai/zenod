### Strict reading

Counting only answers with no error text, the three full runs score **9, 8, 8**.
- **Snapshot changed (Q9 in run 2, Q2 in run 3).** Both happened while `zenod-bot` was filing an agent_team MCP capture into the vault (`memory: ops rollup`, committed 03:48:41Z, between and during those runs). The source changed under the answer, and Zenod refused to mix snapshots, as designed. This is an environment effect like E9-3b's filing lock, not a retrieval miss.
- **Support-selection error (Q7 in run 3).** The model selected a support ID the host had not registered. The host refused that selection, as designed. Sources and lineage still named the right page.

### Q7: one level too shallow (known filing artifact)

In runs 1 and 2 the answer is right but comes from a Log entry that only the level-1 root page cites. The specific depth-3 page doesn't cite that entry, because the E9-2c migration filed the capture as a rollup line on the root. The cited path is true to the vault. Retrieval can't fix this; it needs a filing change, and it was not trivial enough to do here. Proposed: the weekly sweep (E9-2d) or the librarian (E9-2b) re-files such entries onto the deepest page they belong to.
