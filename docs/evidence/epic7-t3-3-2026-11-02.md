### 1. `dokploy`: the only agent path to the Dokploy API

- Runs as root. On VPS1 it re-runs itself with `sudo -n`; from VPS3 it runs on VPS1 over `ssh hetzner_vps_1`.
  Commands: `apps`, `show APP`, `env-names APP`, `env-set APP NAME --stdin`, `env-unset`,
  `deploy|redeploy|stop|start|reload APP`, `api GET|POST`.
- Every response is cut to an allowlist of non-secret keys, at every depth: ids, names, status, image, limits,
  domains, ports, mounts (path and type only). `env`, `buildArgs`, passwords, registry credentials, tokens and any
  new Dokploy field are dropped. Any string left is also passed through the guard's redaction. POST bodies that
  carry env or secret keys are refused, so changes go through `env-set` or `secret put --dokploy`.
- `_raw` (raw JSON) exists only for `deploy-poller`, which must strip a `GIT_SHA` env override. It is root-only and
  documented as "never by hand". The guard covers it (canary test below).
- `tests/test_dokploy.py`: a fake Dokploy whose every app response carries env and passwords (the v0.30 shape). No
  fake value reaches stdout or stderr on any command, including the T3.1 call `application.stop`.

### 3. `agent-output-guard`: the backstop on VPS1 and VPS3

- **Fingerprints:** root on VPS1 builds `/var/lib/alpha9-secrets/agent-guard.json` (0644) from every store value
  (including `.prev`) and every Dokploy env. It stores salted 8-byte BLAKE2b hashes of every 16-character window
  of each secret token (10–15 character tokens are hashed whole), plus names. Config-looking values are skipped:
  URLs without a password, words. First build: 435 values, 262 names, 5573 windows. Rebuilt by root cron every
  10 minutes and after every `secret` write and `dokploy env-set`. VPS3 syncs it from VPS1 every 10 minutes
  (t3agent cron).
- **Hooks**, in Claude Code managed settings `/etc/claude-code/managed-settings.json` on both hosts, so every user
  and seat is covered:
  - `PreToolUse` Bash rewrites the command to `( cmd ) 2>&1 | agent-output-guard filter`. Output is redacted
    before the harness reads it, failures included. Exit code and cwd carry over. A background job holding stdout
    neither blocks the call nor gets SIGPIPE (tested).
  - `PostToolUse` (every tool: Read, Grep, MCP, WebFetch…) returns `updatedToolOutput` with redacted strings. Claude
    Code 2.1.307/2.1.316 supports this for all tools, not only MCP.
  - `PostToolUseFailure` stops the session on a hit, because an error text cannot be replaced.
  - Every hit queues `[SECRET] … <app>/<NAME>` in `~t3agent/agent_team_m0/alerts.pending`. The relay watchdog
    delivers it to the HQ thread within a minute. Names only, rate-limited to one per name per session every
    10 minutes.
- **Coverage:** every Claude Code session on VPS1 and VPS3 started after the install, including T3 threads. T3
  launches `claude` without `--setting-sources`, so managed policy settings load. Sessions already running at
  install time (this worker's own) keep their old hook snapshot until restart.
- **Not covered:**
  - **Codex.** It is installed on VPS1 (0.131) but not logged in (no `~/.codex/auth.json`), and absent on VPS3, so
    no Codex session can run today. Codex 0.131 has PreToolUse/PostToolUse hooks, but untrusted hooks don't run.
    Add and trust the same hook before Codex is ever used there. The wrapper and the key move protect Codex sessions
    regardless.
  - **Values not in the store** (for example Mac-Keychain-only keys) have no fingerprint.
  - **Very short or low-entropy values.** Values under 10 characters are not fingerprinted. Neither are
    config-looking parts of values (hostnames in URLs).
  - **Re-encoded secrets** (base64 of `user:pass`, JSON-escaped `\/`) are not matched. URL-encoded ones are.
  - **The model provider's copy** of the 2026-11-01 session cannot be recalled.

## Part B: the guide

The facts behind its priorities, all checked 2026-11-02 without printing a value:

- **Stripe.** zenod-mt holds the account's **full** live secret key (`sk_live`). No other app in the store holds
  that value (7 `STRIPE_SECRET_KEY` entries, 4 distinct values). Zenod calls only `checkout.sessions`
  (create, retrieve), `subscriptions.retrieve`, `billingPortal.sessions.create` and webhook verification. A
  restricted key is enough. The webhook endpoint is `cloud.zenod.dev/webhook`. No GitHub repo secrets.
- **OpenRouter platform key.** Monthly limit $26, usage $2.19, $24.05 remaining. The worst case is capped. The
  provisioning key is only in Jordi's Keychain.
- **Google client secret.** `GOOGLE_OAUTH_CLIENT_SECRET` equals `GOOGLE_OIDC_CLIENT_SECRET`, on client
  `153584019437-32d9p8q5…`. It cannot be used without a user's authorization code, which Google sends only to the
  registered redirect URIs.
- **GitHub client secret.** One value shared by zenod-mt, phylax, callisthenes, herald and ring (client
  `Ov23lihBhL9ceTqYWKSP`). It needs a user's code from the registered callback.
- **TypeSafe.** The only user is zenod-mt's optional Jev fast path. `classifyFallback.ts` delegates to the primary
  classifier on any failure, so turning it off is cheaper than rotating it.
