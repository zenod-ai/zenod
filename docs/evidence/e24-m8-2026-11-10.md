# DeepSeek filing replies pass the format again (E24-M8, 10 Nov 2026)

**Bottom line. About half of DeepSeek's filing replies were thrown away whole because the model mixed up two lists of ids that look the same. Add candidates now get their own ids, and one wrong operation no longer sinks the rest. On the same live slice, failed reconcile calls went from 17 of 32 to 0 of 24; ingestion and retrieval are unchanged.**

Row M8 in [EPIC-24](../zenod-errors-now-find-fix-and-monitor-so.md). Run: run_231ce603-4662-4aeb-978d-cb8d74ebde23. Found by [E15-Q3](e15-q3-2026-11-10.md). Code: [#1603](https://github.com/zenod-ai/zenod/pull/1603).

## What failed

Both runs replayed every cached call and sent the rest to DeepSeek (`deepseek-flash`, thinking off, JSON mode) through a private capture proxy on VPS3; the raw replies stay in `~/zenod-eval/m8/` (0600) and never enter the repo. Every reply finished with `stop`: no truncation, no thinking text, no JSON parse errors. Classify passed on all 7 of its calls. Every failure was reconcile's operation shape:

| Failure in a reconcile operation | Operations | Calls with it |
|---|---|---|
| ADD writes the source words instead of the asked-for dash in `sourceQuote` | 53 | 12 |
| ADD cites a context source instead of an add candidate | 40 | 11 |
| LINK, CONFLICT or CLARIFY cites an add candidate instead of a context source | 8 | 5 |
| CLARIFY cites no source (`too_small`) | 1 | 1 |

17 of 32 reconcile calls had at least one, and one bad operation made the whole reply fail (`invalid_union` at `operations[]`), so every idea on that page fell back.

**Cause.** The host names add candidates and context sources the same way, `source:<start>:<end>`, and a candidate is a slice of a source, so the ids overlap in range and look alike. The schema still tells the lists apart, but DeepSeek's JSON mode only sees the schema as prompt text and does not enforce it.

## Fix

In `AiSdkBrainLlm.reconcile` (`packages/core/src/llm/aisdk.ts`); the engine, the host checks and the stored ids are unchanged:

1. The model sees add candidates as `add-1`, `add-2`, …; the host's ids come back after the call.
2. A reply that fails validation goes through a repair step. An ADD's `sourceQuote` becomes the dash, because the host ignores that field and saves the candidate's exact words. Each operation is then checked against the same schema. A wrong one is dropped together with every operation on its ideas, so no idea is half decided. Those ideas stay unassigned, and the host files them again with the reason. The repaired reply is still checked against the full schema, and a reply that cannot be read still fails as before.
3. Production logs one line per repaired reply: `[reconcile] {"dropped":{"operations":n,"ideas":m,"issues":[…]}}`, which holds counts and issue codes only, never text.

Tests (`packages/core/test/aisdk-deepseek-background.test.ts`) replay each failure shape above through the real DeepSeek client with a stubbed network, with production's id forms and made-up text.

| Ingestion success | 87.5% | 87.5% (7 of 8) | 87.5% (7 of 8) |
| Retrieval, right memory in the top 5 | 90% | 90% (18 of 20) | 90% (18 of 20) |

| of which answers missing the facts | the stand-in never answers | 3 | 3 |

The filing share of the error rate is now the stand-in's: 1 of 28, 3.6%. The other three are answers that leave out a needed fact. The live tier counts those and the stand-in cannot, and they replayed from the cache in both runs, so a filing fix cannot move them. They belong with answer quality (EPIC-12), not here. After the fix, the live tier's own failure count is zero: no call is wasted.
