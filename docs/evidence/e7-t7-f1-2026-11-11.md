# T7-F1 evidence: new-user Google Drive vault fails on production (2026-11-11)

Row: [EPIC-7 T7-F1](../EPIC-7-REAL-USER-TEST.md). Worker run `run_ce7a0b7c-bfcd-4632-b436-bfa70ceadc60`.
Found in [T7 round 4](epic7-t7-r4-2026-11-11.md) F1: a brand-new user on production `sha-d9ebdd6` connected Google Drive. Zenod made the `Zenod Vault` folder and its first files, then said "could not verify the durable Drive vault". After that, retry and reconnect returned 503.

## What the production log shows

Read-only `docker logs` for container `zenod-mt` on `sha-d9ebdd6`, tenant `user-usr_b17aca0546e8bae00b08256f`:

- `05:36:24Z Google Drive vault callback failed: Drive interleaving at .git/repository.bundle could not be identified in blob revision history`. This is the first connect, and the real failure.
- `05:38:39Z [ops-alert] ... api=/api/vault/drive/recover status=503`, from "retry recovery".
- `05:40:00Z Google Drive vault callback failed: Drive Git bundle checksum mismatch`, from the reconnect. This is a result of the first failure, not a separate fault.

## Cause (reproduced live against the real Drive API)

The agents' sign-in browser (operations@alpha9.io profile, CDP 127.0.0.1:9333) got a 1-hour `drive.file` token. The unchanged `DriveVaultRepository` and `DriveClient` code was then run against that account's real Drive:

1. **Drive returns `appProperties` in no fixed key order.** The upload PATCH response listed the bundle's keys as `zenodVaultRole, zenodVaultBinding, zenodOperationId`. A GET on the same unchanged file straight afterwards listed them as `zenodVaultRole, zenodOperationId, zenodVaultBinding`. `isMetadataOnlyAdvance` compared the two with `JSON.stringify`, so Zenod's own correct write looked like someone else had edited the file. The capture step then found no foreign revision (every new revision is ours), raised the terminal "could not be identified", and closed the journal `failed`. By then the bundle on Drive already held the new bytes, while the manifest still named the old bundle checksum. From that point every open, retry and reconnect stopped at `Drive Git bundle checksum mismatch`, which the server returns as 503.
   - Unfixed code, live: the bootstrap and first save failed in 2 of 2 runs, once on the bundle and once on `.zenod/manifest.json` (the key order is random).
   - Unfixed code, live: reopening the half-made vault returned `Drive Git bundle checksum mismatch`, the exact production symptom.
2. **Drive bumps `version` by itself.** A few seconds after each write, `version` goes up with no change to content or `modifiedTime` (seen live: 1→3 on the first update, then 3→4 with nothing written). Recovery required the version recorded in the journal to equal the current one, so even after fix 1 an interrupted transaction could not recover. Seen live: `Drive transaction target is not bound to base authority at .zenod/manifest.json`.

This also explains why readiness has listed Drive vault acceptance as not passed since 30 Aug. No real user's Drive vault could ever have finished its first save.

## Fix ([PR #1637](https://github.com/zenod-ai/zenod/pull/1637), `packages/core/src/vault/driveRepository.ts`)

- `appProperties` are compared by their entries, and `parents` as a set.
- Recovery reopens a journal that was closed `failed` by this false alarm. It does so only when Drive proves the failed write is exactly ours: same bytes, same md5, every new revision matching our content, and the right file, name, parent and mimeType. Normal recovery then finishes the save. A vault left half-made, like the T7 account's, heals on its next open, "retry recovery" or reconnect. If anyone else wrote the file, it stays closed.
- Recovery accepts Drive's late version bump when the checksum and `modifiedTime` are the same and the version is not older. This is the rule `samePrecondition` already used.

## Proof

- **Unit tests** in `packages/core/test/driveRepository.test.ts` ("T7-F1: real Google Drive metadata behaviour"). FakeDrive now reorders `appProperties` keys between reads and bumps versions late, as real Drive does. A half-made vault is built in the production shape, plus a foreign-write negative case. Without the fix the tests fail with the two production errors (`Drive interleaving at .git/repository.bundle could not be identified…` and `Drive Git bundle checksum mismatch`). With the fix, the whole file passes 65 of 65.
- **Live, real Drive API, fixed code** (T7 account, `drive.file`):
  - bootstrap, first save, a second save and a cold reopen from an empty machine passed in 3 of 3 runs
  - three half-made probe vaults (two failed on the bundle, one on the manifest) all reopened, finished the pending first save and showed the schema files
- **Clean-up:** the probe folders were trashed on the T7 Drive (restorable for 30 days), the token was revoked and shredded, and the browser was stopped. The production T7 vault was not touched: `drive.file` cannot see files that Zenod's own client created.
