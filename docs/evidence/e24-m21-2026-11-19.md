The cause was neither memory (M3 and M15 were) nor a deploy. The Hetzner Cloud Volume that holds all of Docker hung twice for about 16 minutes. Zenod blocked on it, failed its 30-second health check (5 s × 6), and swarm replaced it. The new container also had to start from the hung disk, so the site gave 502 until the volume answered again.

## 2. Fix

- **Not changed in Zenod:** memory limit (it never neared 640 MB) and the health check (any tolerance under 16 minutes still trips, and a process blocked on disk cannot serve anyway). Decision row D on EPIC-24.
- **Host storage is infra-vps's part:** desk note to infra-vps with the windows and `sar` lines. Their options: Hetzner support ticket, moving Docker's root off the volume, an alert on sdb await.
- **Our alarm (this row's fix):** [#1704](https://github.com/zenod-ai/zenod/pull/1704). When zenod.dev or cloud.zenod.dev is red, the watchdog also writes one daily note into **Zenod's own desk inbox**, which is part of the Delivery Manager's next wake. It writes only when the red set changes, and a recovered page stays listed as "green again at HH:MMZ". Tests pass. I ran it end to end on VPS1 against a throwaway repo.

## 3. Why zenod-social saw it first

The alarm did fire first: 06:12:04Z, 49 minutes before their note. It went only to the "HQ — vps1 alerts" thread, which wakes no agent. That thread carried ~40 alerts that hour (row-2 "sha behind", row-7 poller, row-19 AI credit, row-14…), so a real outage looked like the chronic reds. During the second hang the relay itself waited 15 minutes (07:12:58Z for a 06:58:13Z alert). The desk-note path now reaches the Zenod desk directly; the HQ thread's noise is noted for EPIC-6.
