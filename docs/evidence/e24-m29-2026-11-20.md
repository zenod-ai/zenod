## Answer

The leaked key is held by exactly two dead test tenants (retire approved, M28). Nothing real pushes with it. The argv leak is closed and live on production `6b619b9c`.

```
before   git clone/remote set-url  https://x-access-token:<KEY>@github.com/...   key in argv (ps) and .git/config
after    git clone/pull/push       https://github.com/<repo>.git                 key only in the git process env
```

## 1. The argv fix (PR [#1720](https://github.com/zenod-ai/zenod/pull/1720), squash 6b619b9c, ci green)

- `packages/core/src/git/vaultRepo.ts`: the remote is always the plain `https://github.com/<repo>.git`. The credential travels as `GIT_CONFIG_COUNT=1`, `GIT_CONFIG_KEY_0=http.https://github.com/.extraheader`, `GIT_CONFIG_VALUE_0=AUTHORIZATION: basic <base64 x-access-token:key>` on the one git handle (same shape as agent_team `worldGithub.ts` `gitEnvFor`). A rotating App token refreshes the env before each remote call; no `remote set-url` per call any more.
- On open, an origin an older build wrote with a key in it is rewritten to the plain URL (cleans old `.git/config` files), also when no repo is given.
- simple-git blocks editor/pager/askpass/ssh/config-path variables in a spawn environment; those inherited variables are left out of the vault git environment, and only `allowUnsafeConfigEnvCount` is enabled for the one count we set.
- `packages/core/test/vaultRepoCredential.test.ts` (5 tests, plus the existing git and config-lock tests: 15 of 15 pass): a wrapper `git` on PATH logs every argument list; clone, pull and push run for real through a local bare repo; the log has no key and no `x-access-token`, the wrapper saw the extraheader env, `.git/config` has no key, and a legacy keyed origin is cleaned.
- Live: staging and then production run `6b619b9c` (rolled 22:06Z, gate: demo 96/100/1.7, real notes 100/91.2/1.6). `ps` on VPS1 after the roll shows no key-bearing git process.
