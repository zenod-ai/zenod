## Misses and their causes

1. **No source read (Q4, Q9; 8 of 59 answers).** The usage ledger for Jordi's tenant (metadata only: tokens per call) shows that each failing ask is a short model call with about 140 output tokens. The model never executed a read: it answered from the briefing's page map, and the host refuses unread prose (`I couldn't verify an answer…`). This predates E9-3b: baseline Q4 failed the same way on `bfc6e9b`. #1463 forces a search or read in round 1, and #1464 retries an ask that made no tool call. Q4 and Q9 then passed in some runs and still failed in others. The ledger shows that a failing ask after #1464 made two calls, and neither executed a read. The model `ask_brain` runs is `deepseek/deepseek-chat` through OpenRouter, which does not reliably honour `tool_choice: required`. The tenant setting `model_ask` names a different model (`openai/gpt-5.6-luna`), so the configured ask model is not the one MCP `ask_brain` uses.
   **Fix (proposed row, below):** when an ask ends with no read, the host itself runs `search_vault` on the question and reads the top placed page, then answers from that read, as the pinned-evidence path already does. Also check why MCP `ask_brain` does not use the tenant's `model_ask`.
2. **Lineage one level up (Q7; 3 of 6 runs).** In those runs the answer came from a Log entry that only the level-1 root page cites. The specific page never cites that entry, because the E9-2c migration filed that capture as a rollup line on the root. The cited path is therefore true to the vault, just shallower than the question's natural page. **Fix:** a filing change, not a retrieval one. The weekly sweep (E9-2d) or the librarian (E9-2b) should file such entries onto the deepest page they belong to.
3. **Filing lock (Q6, once) and a container swap (Q10, once).** These are environment effects during the run, not defects.
