# T7-F6: a single paid answer is no longer thrown away by Zenod's own vault refresh (2026-11-13)

Row: T7-F6 in [EPIC-7](../EPIC-7-REAL-USER-TEST.md), from [E7-S4](e7-s4-2026-11-13.md). Run: run_7aac5483-193f-47e7-94ef-cd485339a7e3. PR [#1653](https://github.com/zenod-ai/zenod/pull/1653), merged as `b5234d29` after `ci` passed (12 min 33 s).

**Bottom line.** No filing caused the two billed non-answers. Inside the answer, Zenod refreshed the vault from Google Drive, and on a Drive vault that refresh holds the vault lock for several seconds. The answer's note read waited 3 s, gave up, and the paid answer was replaced by "Memory filing is in progress". Now a read waits for that refresh to finish. A real filing still gets the retry line.

```
before:  question ─► model ─┬─ search_entries ─► vault refresh (Drive pull, lock held for seconds)
                            └─ read_note ─► waits 3 s ─► "busy" ─► paid answer dropped, retry line sent
after:   question ─► model ─┬─ search_entries ─► vault refresh
                            └─ read_note ─► waits for the refresh ─► reads ─► answer kept
```

## Cause, from production and code

| Evidence | What it shows |
|---|---|
| Production `zenod-mt` log 02:40–02:53Z (sha-e0100de, read with the VPS1 sudo allowlist, no content) | the T7 account's 4 chats ran one at a time. No filing (`[task-job]`) for that tenant around 02:45 or 02:51. No other answer was running |
| `GET /api/vault` for this account took 4958 to 13175 ms | reading the Drive revision (manifest plus Git bundle download and check) takes about 5 s. A Drive pull does at least that much work |
| `engine.ts` `readTools.searchEntries` → server `searchMemoryEntryPage` → `engine.searchEntries` → `syncForRead()` | each answer that lists entries starts a read-sync pull once the 60 s refresh window has passed. The pull holds the vault lock through `queue.run` |
| `safeReadRevision()` waits `readLockWaitMs` = 3000 ms (T7-F3) | a parallel `read_note` / `read_facts` hits `VaultWriteBusyError`, `readBusy` is set, and `finalize` returns the retry line after the model call has been paid |
| T7-F3's 3 s wait was set for GitHub vaults, where these holders take milliseconds | on Drive they take seconds, so a single answer collides with its own refresh |

## Fix (packages/core/src/engine/engine.ts, +10 −3)

`syncForRead` records the pull it has in flight. `safeReadRevision` waits for that pull (its errors are ignored) before it takes the lock. A pull only reads the vault and always ends, so this is never the minutes-long wait behind a filing (#96). Filings and other writers still turn a read away after 3 s as before. `ask` still checks for a busy vault before its model call (T7-F3). Chat replies are unchanged (root L-6).

## Test

`packages/core/test/engine.test.ts` "a single chat answer is kept when its own entry search pulls the vault meanwhile (T7-F6)": one `handleTasking` question (the `/api/chat` path), the pull slowed to 400 ms, a probe wait of 100 ms, the model calls `search_entries` and then `read_note` while the pull runs, as on production.

| | on `main` | with the fix |
|---|---|---|
| reply | **"Memory filing is in progress…"** after 1 billed model call (the production symptom) | the answer, 1 model call |
