The refactor's actual scope

What stays vs what dies

KEEP — the product (and the moat)

  • The brain: governed memory, evidence, citations — untouched under every option
  • The council as authorities: Zenod only writes the vault, Archus the backlog, Callisthenes the voice, Phylax the door
  • Receipts: no claim without same-turn evidence (stronger than anything frameworks ship)
  • The living iteration document — it's the state artifact, not inter-agent mail
  • Canonical tests C-01…C-20 — they become the acceptance suite for ANY new engine
  • Positioning deck V5: "gatekeepers keep order" IS the new model, already

DELETE — the plumbing (now commodity)

  • Agents talking to agents to get work done (peer chatter, handovers, lost context)
  • Three front doors to the backlog, silent-ack routers, regex guards
  • Bespoke fan-out scheduling and worker-spawn glue
  • Durability by reconstruction (usage ledger after redeploys)
  • Custom stream/lifecycle plumbing per lane

The office analogy holds better than before: it was never five people mailing files to each other — it's one OS running five applications, each with an exclusive lock on its own file type.

New model

One owner of the situation. Two species of tool.

THE ORCHESTRATOR — one context owner frames tasks · absorbs results · writes the living doc · talks to you
↓ spawns (call/return, hard budgets)      ↓ calls (receipt-or-error, single writer)

WORKERS — sub-agents = tools with judgment inside

  • · Born for one task, fresh context, die after
  • · Return a structured summary, never chat sideways
  • · Run in parallel — async execution, sync accountability
  • · Killed at budget: no more 406-turn zombies

OWNERS — governors = authoritative gateways

  • · Zenod — only writer to the vault
  • · Archus — only writer to the backlog (ONE door)
  • · Callisthenes — the only public voice
  • · Phylax — the only door to your attention

It is still a council. The council was always the org chart — who owns what — not the network diagram. You still talk to your team; the names, roles and taste survive. What's gone is governors passing work to each other conversationally. The living document is the orchestrator's state — workers' results land in it, and it goes back to the planner each iteration. Document-passing between peers dies; document-as-single-source-of-truth is promoted.

The posting loop in the new model

1Voice note lands. Orchestrator frames one task: "propose 5 posts on the memory angle, cite sources." one context owner from here on
2Sub-agent spawns with Zenod's MCP tools mounted. It reads memory through Zenod — search_memory / get_memory — never raw GitHub, never spoon-fed by the parent. state flows through its owner; that's what the owner is for
3Sub-agent returns structured proposals + citations, then dies. this is already how the runner works today — workers mount the console MCP
4Orchestrator writes the backlog via Archus (one door, receipt-or-error), ranks the queue.
5Queue drains throttled via Callisthenes — the only voice. Publish receipts land in memory via Zenod.
6Feedback and your nudges → Zenod store → next framing is smarter. the loop learns; the moat compounds

Same loop as the user-journeys deck. Nothing in the product story changes — "one agent at the end of the day" is exactly what the customer always experienced.
