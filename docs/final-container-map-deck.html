Self-hosted vs hosted: literally the same image

One repo per unit, one Dockerfile, one image on the registry. There is no self-hosted build. The difference is boot-time configuration only:

Hosted (your VPS)Self-hosted (customer's box)
ImageIDENTICAL — same registry tag
BootEmpty; waits for tenantsZENOD_API_TOKEN env → chassis auto-inserts ONE tenant row at startup
New userStripe webhook → POST /api/tenants (needs CONTROL_PLANE_TOKEN)n/a — endpoint dead because no control-plane token is configured
MeteringSame code, enforced per row against plan; block-at-zeroSame code, plan = unlimited — meter still records, never blocks. Costs tab works for free
UIFull console, tenant-scoped loginSame full console — wizard, settings, everything. Not a stripped product
DBShared DB / per-unit store, N rowsSame store, 1 row (SQLite on the volume — zero extra infra)
Run itDokploy appdocker run -e ZENOD_API_TOKEN=… -v data:/data zenod-ai/zenod

Why this matters: every self-hoster QAs the exact code your paying tenants run. No fork, no drift, no "community edition." And the public repo stays honest — the multi-tenancy is invisible at N=1 because it's just a table with one row.

Suites (Herald, Council…): UI + DB containers that "inject a user"

A suite ships no MCP characters of its own. It is a thin container — UI + its own small DB — that holds machine-tenant tokens into the base characters. Buying Herald = the control plane provisions a tenant row in each composed unit and hands the tokens to Herald's wallet. Your words, now law (D3): "one Zenod container ever — literally the same container; suite users are just more tenant rows."

herald UIdb

  • Inside: Herald's product UI + suite config DB + wallet of agent→unit tokens. That's all.
  • Configures Zenod/Callisthenes/Epaminon for its users by calling THEIR APIs with ITS tokens
  • Own users, own pricing, own metering rollup — units just see another tenant

council / future combos UIdb

  • Same recipe: thin UI+DB container, machine tenants into base characters
  • New product = new thin container + N tenant rows. Never a new copy of a character
  • Kill a suite → delete its container + revoke its tenant rows. Characters untouched

So the fleet's growth law: base characters stay at ~7 containers forever; each new PRODUCT adds exactly one thin UI+DB container. Users never add containers anywhere — anyone's users, any product, are rows.
