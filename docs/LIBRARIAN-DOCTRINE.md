# Librarian Doctrine

How the librarian organizes the vault, distilled from community evidence (Reddit, HN, Obsidian forum, practitioner repos, 2024–2026; researched 2026-06-10) plus Karpathy's llm-wiki pattern. Companion to [M0-SPEC.md](M0-SPEC.md) — these are the rules the engine enforces in code.

## The reference point (Karpathy, primary sources verified 2026-06-10)

Karpathy's ["LLM Knowledge Bases" post](https://x.com/karpathy/status/2039805659525644595) (April 2026) and the companion [llm-wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) (2026-04-04) ignited the current wave. Verified verbatim from the gist:

- *"Instead of just retrieving from raw documents at query time, the LLM incrementally builds and maintains a persistent wiki."*
- Raw sources *"are immutable — the LLM reads from them but never modifies them."*
- The wiki is *"a directory of LLM-generated markdown files… The LLM owns this layer entirely,"* with a schema file *"(e.g. CLAUDE.md for Claude Code)"* read first.
- *"You're in charge of sourcing, exploration, and asking the right questions. The LLM does all the grunt work."*

His [Farzapedia endorsement](https://x.com/karpathy/status/2040572272944324650) explicitly prefers an **explicit, inspectable markdown memory artifact** over the *"status quo of an AI that allegedly gets better the more you use it"* — i.e., markdown-vault memory over opaque DB memory. Supporting frame: his [LLM OS](https://x.com/karpathy/status/1723140519554105733) (context window = RAM, filesystem = long-term memory).

Zenod is this pattern delivered as a service instead of a manual workflow: filing discipline as code, not willpower.

## Core principle (community consensus)

> **"Procedural code owns the environment. The agent owns content."** (obsidian-mind)
> **"The LLM is the librarian. You're the curator."** (second-brain)

Schema enforcement must be deterministic (validation code, not prompts). The methodology brand (PARA, Zettelkasten, Johnny Decimal) matters less than: sparse predictable structure + machine-readable indexes + a schema doc at root.

## Failure modes we are built to prevent

Documented across practitioner reports:

- **Duplicates** created months apart; same-filename link collisions silently resolving wrong.
- **Tag sprawl** when the agent free-invents taxonomy (duplicate tags, single-use tags).
- **Orphan notes** — "a note without links is a bug" (obsidian-mind).
- **Vault pollution / AI slop** — the deepest objection (Späti, "Keep AI Out of Your Vault"): over time you can't tell your thoughts from generated filler.

Anti-slop answer: **provenance is first-class.** Human-authored vs agent-written is always distinguishable — the git contract gives this for free (commit author identity + per-fact capture links). Agents never edit human-authored thinking notes.

## Vault rules (the meta-schema, fixed in code)

1. **Two tiers.** Immutable captures (`Inbox/`, `Log/`, `_attachments/` — append-only, never edited, source-linked) and distilled pages (`Areas/`, `Projects/`, `Notes/` — entity-centric, regenerable, every claim citing its captures).
2. **Shallow purpose folders only.** Folders are coarse routing; deep hierarchy fails agents.
3. **Links over folders.** Every distilled page links to related pages (or the `Tree`); orphans fail validation. Each page also names its `parent` in the memory tree (below).
4. **Minimal enforced frontmatter**: title, type, tags (controlled vocabulary), created, updated, summary. New/rewritten pages also carry OKF-compatible `description` and `timestamp` aliases. Enables cheap two-pass retrieval: scan titles/tags/summaries first, open bodies only when needed.
5. **Schema doc at root** (AGENTS.md) — the agent reads it first; validation code enforces it regardless.
6. **Meta-schema fixed; taxonomy evolves by proposal.** Folder set, frontmatter keys, naming, linking rules change only via versioned migrations. Tags/MOCs evolve through explicit, logged proposals. Zenod is a strict OKF profile: OKF compatibility is an interoperability layer, not permission to weaken Zenod lint.
7. **Entity pages are the primary write target.** Distillation lands on interlinked entity/topic pages, not a journal — the Log stays as a raw source, so knowledge compounds instead of accumulating.
8. **Write distilled pages for LLM readers**: dense, self-contained, explicit links — a page must survive being dropped cold into a context window with no implicit shared context.

## Memory tree (EPIC-9, schema v1)

Pages hang in a tree so that a memory's path from the root *is* its context ([E9-1 audit](epic9/E9-1-memory-structure-audit.md) §4–§5). Code: `packages/core/src/vault/tree.ts` (schema, parsing, lineage), `treeLint.ts` (lint), `treeSeed.ts` (seed).

- **Level 0** is fixed: two groups, **working memory** (ongoing now: a plan, a decision in progress) and **long-term memory** (durable facts, preferences, runbooks, finished things). The Log is the evidence underneath, not a branch.
- **Level 1** is the vault-root `Tree.md`: one line per root node under a `## Working memory` or `## Long-term memory` heading. Zenod generates it (E9-2g, below; frontmatter `generated: zenod-discover`); nobody picks the roots by hand. The form is
  `- <name> | working|long-term | [[<page path without .md>]] | <one-line summary>`.
  Tree.md never holds deeper levels; nested bullets fail lint.
- **Page frontmatter** carries the rest of the tree:
  - `parent:` a wikilink or vault path to the parent page (`"[[Hair transplant]]"`, `"[[Areas/Life admin]]"`; quote it in YAML). A level-1 root page carries `parent: "[[Tree]]"`.
  - `memory: working | long-term`. Required on root pages and equal to their Tree.md group; optional below, and when present it must match the root the page hangs under (a page inherits its root's group, so closing a working root and moving it under a long-term node needs no rewrite of its children).
  - `provisional: true` (optional) marks a node created because nothing fitted (filing rule 4); the sweep reviews it.
- **Scope.** Every meaning page (`Areas/`, `Projects/`, `Notes/`, minus index pages) is placed. Log entries, Inbox files and `_attachments/` are not tree pages.
- **Lint (`zenod tree lint`, `lintTree()`).** Errors: Tree.md missing or malformed; a node whose page is missing, or whose page lacks `parent: "[[Tree]]"` and the matching `memory:`; a page without `parent`, with a parent that does not resolve to a meaning page, or with `parent: "[[Tree]]"` but not listed in Tree.md; a cycle; a page deeper than level 6; a `memory:` that disagrees with its root. A page below a broken ancestor is not reported twice. Duplicate titles are warnings. The report also counts Inbox machine files (needs-filing stubs, receipts) and markdown outside the schema folders.
- **Lineage (`buildTreeIndex().lineage(path)`)** returns the steps root → leaf and the group; `formatLineage` renders `Working › Hair transplant › 2023 Barcelona quotes`. `children(path)` lists a node's direct children. Retrieval (E9-3a), the librarian (E9-2b) and the sweep (E9-2d) use these, not their own parsing.
- **Seed (`zenod tree seed`).** Prints the audit's proposed Tree.md, or with `--out <dir>` writes Tree.md plus one lint-clean root page per node into an empty directory. It never overwrites; moving an existing vault into the tree is a reviewed migration (E9-2c), not a seed.
- **Filing into the tree (E9-2b, `packages/core/src/engine/treePlacement.ts`).** Every capture still lands in the daily Log first. Once the librarian has filed it:
  - *Placement (rules 2–4, only when the vault has a `Tree.md`).* A page the filing wrote that has no resolvable lineage gets `parent:` set to the best-matching node. Matching walks down from the roots, scoring token overlap with node names (×2) and summaries. A deeper page wins only when its own name matches, so leaves do not chain under siblings, and provisional pages never adopt others. A weak match also sets `provisional: true`. A capture that reached no page (an Inbox question, an uncertain topic, or a classified capture where nothing fitted) becomes a provisional leaf in `Notes/` under the closest node, quoting the capture and citing its entry. The touched pages must pass `lintTree()` and `zenod lint`, otherwise the placement is undone and only a plain `filed:` line is written.
  - *Root-only filings reach the leaf (E9-2f).* When a filing (not an ops rollup) reached only level-1 roots, the deepest page below each root that matches it also gets the capture as a line in its `## Captures` section: `- 2026-10-23 · <one-line summary> [[2026-10-23#^e-…]]`, and a `filed:` line of its own. The bar is stricter than placing a page (`citeOnLeaf`): the page's own name must match a word the root's name and summary do not already carry, and the score must be at least 3. The root keeps its citation; retrieval lineage picks the deepest citing page.
  - *Agent ops reports (rule 5, tree vaults only).* A Watcher read, console decision, wake or test-campaign report skips page filing. `isAgentOpsReport(content, source)`: from any surface, the first line carries an epic, ticket or run id, bare or in parentheses (`(agent_team E46-S9 …)`, `(T3)`, `Run: run_…`), and the text reads as telemetry; from MCP, the CLI or an unknown surface, also anything the capture-origin check reads as an agent report (E9-2h). A person's own WhatsApp note naming an ask (`Approve E7-A12`) still files normally. It becomes one dated line in the `## Ops rollup` section of its level-1 project node, e.g. `- 2026-11-01 ops (2): [[2026-11-01#^e-…]], [[2026-11-01#^e-…]]`. The node's `updated:` is left alone, so ops traffic never makes a root look ongoing; the weekly sweep (E9-2d) must not count the section as activity.
  - *`filed:` back on the Log entry (rule 6, every vault).* The line is appended, never inserted, so the Log stays append-only: `- filed: [[Notes/X]] (Working › Hair transplant › X)`, with `· provisional` or `· ops rollup` when they apply. A tree-less vault gets `- filed: [[Notes/X]]` without the path. When nothing was worth a page, it gets `- filed: log only (reason)`. If the entry is no longer the last one in the file, the line names it: `- filed e-1a2b3c: …` (no caret, so anchors stay unique). Each page is recorded once per entry (`parseFiledLines` reads both forms). Filings still pending a retry write nothing until they settle.
  - *One durable revision per capture.* Synchronous stores and unguarded enrichments carry the placement and the `filed:` line in their own commit. A receipt-guarded topic enrichment cannot add files, so its placement is one follow-up commit, and the returned result reports that revision.
  - A vault without `Tree.md` behaves exactly as before apart from the `filed:` line: no `parent:`, no leaves and no rollups are written.
- **The weekly sweep, the compactor (E9-2d, `packages/core/src/engine/treeSweep.ts`).** Once a week per tenant the sweep tidies a tree vault and decides nothing for the person:
  - *Stale working roots.* A working root whose whole subtree has no capture for 30 days (latest cited Log date or `filed:` line, outside `## Ops rollup`; a page that cites nothing counts from its `created:`) gets ONE proposal line: keep, close (one Outcome line, then it moves under Long-term memory) or fold into another root. The sweep never moves a root.
  - *Pending receipts.* An `Inbox/filing-…` or `Inbox/needs-filing-…` file at least 2 days old, with no filing job still queued for it, is re-filed with E9-2b's placement: if its capture already sits on a page, that page gets a parent when it lacks one; otherwise it becomes a provisional leaf under the closest node. The receipt then moves to `Archive/Inbox/`, byte for byte. Prepared (interrupted) filings and filings pending under a week old are left alone.
  - *Agent-report leaves (E9-2h).* A provisional leaf whose every citation is an agent report (a report the ops filter missed before E9-2h) becomes dated ops-rollup lines on the root it reads most like, and the leaf moves to `Archive/Agent reports/` byte for byte. Leaves with children, and any page holding one of the person's own captures, stay. Count `agentLeavesRefiled`.
  - *Root-only citations (E9-2f).* A Log entry cited only by level-1 roots (outside `## Ops rollup`; for example the E9-2c clean-up's re-filed lines) gets the same leaf citation as a new filing, when a page below that root clears the same bar. Agent ops reports stay on the root (rule 5). Nothing is removed from the root; entries no deeper page fits stay as they are. The counts are `rootOnlyCitations` and `citationsDeepened`, and the commit message names `deepened N`.
  - *Self-organising roots (E9-2g, `packages/core/src/engine/treeDiscover.ts`; EPIC-9 L-1).* The roots are re-derived from the vault, bottom-up, never seeded:
    - *Topics.* Every tree page becomes a TF-IDF vector of its own words (title, summary, tags, headings, body; ops rollups, citations, spoken filler and ingest headers removed), plus three content edges: a body wikilink, a `parent:` to a real page, and the same capture filed on both pages. Average-linkage clustering merges pages while they stay similar (0.13). It is deterministic and costs no model call; embeddings were not needed at vault sizes and would send every page to another provider. Hand-seeded root pages (E9-2a/E9-2c, recognised by their boilerplate line) are aggregators: they join the topic they read most like, or stand alone when nothing is close (a one-page topic such as a hair transplant dossier).
    - *Named subjects (E9-2i, `engine/treeSubjects.ts`).* Clustering only finds subjects that have pages. A product the person keeps naming, which the librarian filed onto other subjects' pages, never had one (Jordi's agent_team, spoken "agent team", sat on Zenod and EpicSpine pages; as two common words it set no page apart either). So the vault's coined names (written somewhere as one identifier: `agent_team`, `EpicSpine`, `Poly-Maker`; not stopwords, spoken filler or ingest words, not ids with digits) are counted in the person's own captures of the last 30 days in any spelling (`agent team`, `Agent-Team`), ingest header lines removed. A name said at least 10 times, in at least 3 captures, on at least 2 days, with no tree page titled after it, gets a page, `Projects/<Name>.md` (`generated: zenod-subject`, `subject: <key>`), with one line per capture: date, how often it names the subject, the words around the first mention, the citation. Agent reports never count. Later runs add the person's new captures to pages Zenod made, and never edit a page someone else wrote. A subject page is a topic of its own with the pages filed under it; it links only the Tree, since a link to the pages its captures were filed on would tie it back into their topic.
    - *Subjects of their own (E9-2i).* A page that holds at least 5 of the person's own captures, nearly all of them (85%) on no other page of its topic, whose title shares no word with the topic's other titles and which is not what most of the topic hangs under, splits off its topic with the pages under it (a family page that word overlap and links had put inside another subject). Subject topics never merge with another topic, and a cold one is a long-term area of its own however small.
    - *Freshness is the person's own activity.* Each Log entry has an origin (`vault/captureOrigin.ts`): WhatsApp, Telegram, web and Drive are the person's; MCP and CLI notes are theirs unless they read as an agent report (ticket or epic ids, also in parentheses; run ids; commit SHAs next to deploy words; PR numbers; wake/Watcher reads; a first word that is a repo or agent slug or a host, as in `zenod-social, 2026-10-28:` or `VPS1 2026-10-30:`); selftest is never theirs. Only the person's captures heat a topic: each adds 0.5^(age/14 days) to the pages it is filed on; one that only a seeded aggregator holds heats the real page it reads most like. Agent reports never heat anything, and ops rollups are ignored.
    - *Working vs long-term, with hysteresis.* A topic is working at heat ≥ 0.9 (about one own capture in the last couple of days, or several in the last weeks); a topic that is already working stays until it falls below 0.3; either way it needs at least one own capture in the last 30 days; at most 8, hottest first.
    - *Near-duplicate subjects (E9-2h).* Two warm topics (heat ≥ 0.3 each) become one when one's name refines the other's (`Zenod deck` and `Zenod`), when most of one's page titles carry the other's name, or when their distinctive words overlap strongly (cosine ≥ 0.5). Cold topics meet in the long-term area merge. The rest merge further by content into at most 6 long-term areas (an area under 3 pages joins its closest neighbour).
    - *Root pages.* A root is a page of its own topic: the one most of the topic already hangs under, weighted by the person's captures on it and by a short, general title; a seeded aggregator counts half, a provisional page never. A root that continues from the last sweep keeps its page.
    - *Names (E9-2h): what the group is about, not one page's title.* Candidates are runs of one to three words from the group's own page titles (never a seeded one) and, for a single topic, the five words its pages and the person's own captures share most. A candidate's reach is the share of the group's pages, of its titles (twice) and of the person's own captures on it that carry all its words; its value is the reach, softened when the words are under e≈2.7× as common inside the group as in the rest of the vault. The name is the best candidate on at least half the pages; a longer phrase holding it wins when it keeps 90% of the value (`Hair transplant`, not `Hair`); the title of the page the group hangs under wins when it is on half the pages and reaches 55% as far (the person's own label, even for a word the whole vault uses, like `Zenod`), unless the person says the title's head in their own captures on the group but never its tail: then the head names it (`Family`, not one page's `Family Holidays & Logistics`, E9-2i). A long-term area made of several topics whose name covers under three quarters of it gets two or three parts (`Idealista and Poly-Maker`). A long-term area about a working root's subject (its own best name is that root's, or that root's name is in its titles and on more of its pages than any other phrase, a third at least) is called `<root> (earlier)`. Working roots are named first. A continuing root keeps its name while the name keeps 80% of the best name's reach and value. Each root also lists its five most distinctive one-word candidates (`terms`). Pages keep a parent inside their topic; the rest hang under the root. Only `Tree.md`, the `parent:`/`memory:` lines and Zenod's own subject pages change; no file is moved or deleted, and the only file created is a subject page. A run repeats until it writes nothing (at most 3 passes); a second sweep on the same day writes nothing.
    - *Run by hand:* `zenod tree discover [--today YYYY-MM-DD] [--fresh] [--json]` prints the roots; `--apply` first moves agent-report leaves to the ops rollup (above), then writes the roots (no commit). The first run over a hand-seeded tree ignores the old roots (`fresh`).
    - *Stable identity (E9-5b, `engine/treeIdentity.ts`).* Each root carries an id, written as an Obsidian block id at the end of its Tree.md line (`^n-1a2b3c4d`, hidden when reading). A re-derived root inherits the old id it shares at least half its pages with (Jaccard ≥ 0.5, one-to-one, largest overlap first, ties by old id); a new root gets `n-` + 8 hex of sha1 over its sorted pages. A root written before ids existed gets the id its pages would get, so the first run with ids changes nothing else. A root whose re-derived name is its previous name's parts in another order (`Poly-Maker and Idealista`) keeps the previous one. Heat, Jaccard and the id rule are the shared tree library also in the EpicSpine skill (`scripts/spine_tree.py`); `packages/core/test/fixtures/tree-library-parity.json` is a copy of the skill's fixture, and both sides must pass it. Zenod never imports the skill.
    - *Steering (E9-5b, `vault/treeSteering.ts`): the person's word wins.* `## Keeper notes` in Tree.md, one line each, `- K-<n> | applies to | rule | why | confirmed YYYY-MM-DD`, the vault's Operating Learnings. "Applies to" names roots or pages (comma-separated), each optionally with its id (`House ^n-1a2b3c4d`); a name resolves to the root of that id, else of that name or one of its aliases, else a page of that title. Rules: `pinned` (never demoted, never renamed, its page stays the root), `name: <Name>` (the root keeps the person's name; no other root may take it), `aliases: a, b` (read as the root's name in clustering, mirrored into the root page's `aliases:` so Obsidian and the index find it), `keep apart` (those roots or pages never share a topic or area, even when the area cap would merge them), `own root` (a topic of its own, like a subject page). Two steered pages never share a root. The root page mirrors the flags (`pinned: true`, `name-locked: true`, `aliases: [...]`); a person may set those flags by hand too. Flags and aliases are only ever added; notes are only ever appended; a re-derived Tree.md carries `## Keeper notes` and `## Recent changes` over verbatim. A note naming nothing in the vault is reported (`steering.unresolved`) and kept, not acted on. Tree lint rejects a malformed note and a repeated id.
    - *Pin and rename in the Memory tab (E9-5b).* `POST /api/console/memory-tree/steer` (`{action: "pin" | "rename", root: <id or page path>, name?}`), same-origin, tenant from the session's account only. The engine's `steerTree` takes the interactive lane of the vault write queue, the lock a filing takes: it appends one Keeper note, sets the root page's flag (and, for a rename, the Tree.md line), lints, and commits it as one revision, `memory: keeper note K-<n> (pin X | rename to Y)`; any failure reverts it. A name is 1–60 characters without `| ^ [ ] #` and not another root's.
    - *Steering by message (E9-5e, `engine/steerMessage.ts`).* A short text message over WhatsApp, the web or MCP (`chat`, `handleTasking`) is read as a steer before the model and before any filing, so it is never filed as a memory: "pin X" / "fija X" / "fixa X"; "rename X to Y" / "renombra X a Y" / "reanomena X a Y"; "X is Y" / "X es Y" / "X és Y" (an alias: plain form only when Y is a root and X is not, so "Zenod is great" stays chat; "X means Y" / "X es lo mismo que Y" either way); "X is not Y" / "X no es Y" / "separa X de Y" (keep apart; both sides must be roots); "yes, close X" / "sí, cierra X" / "sí, tanca X" (a `closed` note: the next run puts the root in long-term memory and keeps it there until a later pin; the later of a pin and a close wins); "that's wrong" / "eso está mal" / "això està malament". Roots resolve by id, name or alias, ignoring case, accents and `_`, else by every word of the name; none or several gets a short question back, never a guess. Each steer is one Keeper note through `steerTree` (one commit under the vault write lock, `memory: keeper note K-<n> (…)`), and the reply says in plain words what changed and how to undo it, prefixed `Memory tree:` / `Árbol de memoria:`. A bare "that's wrong" is an undo only right after such a reply (otherwise it is about the last answer); "undo the last tree change" / "deshaz el último cambio del árbol" works any time. The undo reverts the newest keeper commit (`memory: keeper…`, `memory: weekly tree sweep…`, `memory: tree…`, `memory: undo…`) with `git revert --no-commit` as one new commit `memory: undo <sha> (…)`: never a force-push, never Log/ or `_attachments/`, refused when it does not apply cleanly; saying it again restores. Voice notes still go to capture; steer by text. `messageSteering: false` turns it off.
    - Counts `discoveredWorking`, `discoveredLongTerm`, `rootsNew`, `pagesReparented`; the commit message names `roots N working / M long-term`. The sweep's `zenod lint` gate rejects only errors the sweep introduced, since re-rooting touches old pages that may carry lint debt.
  - *Duplicate titles.* Pages sharing a title get one merge proposal line (keep the placed, shallowest one). Nothing is merged.
  - *Where proposals go.* One vault page, `Inbox/Tree sweep.md`, rewritten only when its proposals change; the console reads a one-line count summary from `GET /api/console/memory-sweep`.
  - *Safety (E9-A2, "raw data stays safe").* Nothing is deleted (a removed Inbox receipt must have its exact bytes under `Archive/Inbox/`, a removed agent-report leaf under `Archive/Agent reports/`), `Log/` and `_attachments/` are never written, tree lint may not get worse, and all of a sweep's changes are ONE vault commit (`memory: weekly tree sweep (…)`), so `git revert` undoes it. Any failure reverts the working tree and commits nothing.
  - *Schedule.* A `tree_sweep` job on the tenant's durable task lane, queued by the per-tenant monitor tick in the first 02:00–06:00 UTC window from Sunday 02:00 UTC, keyed `tree-sweep:week:<Sunday>` so it runs once per week across restarts. The lane is serial and the engine takes the vault write lock on its background lane, so a sweep never runs alongside a live filing. `GET /api/memory/sweep` shows the next run and the last run's counts; `POST /api/memory/sweep/run` runs one now.

## Human-in-the-loop points

- **Autopilot**: filing/updating single notes from a capture.
- **Ask-when-unsure**: classification confidence low → ask, don't guess.
- **Proposal-first** (never auto): renames, merges, moves, bulk migrations, taxonomy changes. Plan approved before execution. One exception, by the owner's decision (EPIC-9 E9-A4, L-1): the weekly sweep re-derives the tree's roots on its own (E9-2g). It only rewrites `Tree.md` and `parent:`/`memory:` lines, as one revertable commit.
- **Periodic audit** (e.g. every ~10 ingestions or nightly): dupes, orphans, broken links, stale claims surfaced as proposals, not auto-fixed.
- **Append-only operation log** of every librarian action (we get this from git, plus `Log/` entries).

## Retrieval strategy

Community evidence: BM25/grep finds the right note >90% of the time under ~1K notes when one person writes and searches; Anthropic itself replaced Claude Code's vector search with grep. But agent-written notes erode the "same author, same vocabulary" assumption — vocabulary mismatch is the failure case.

- **v1 (M0):** lexical only — grep/ripgrep over bodies + frontmatter index pass. No embeddings.
- **Add semantic when**: vault >~1K notes, or human+agent vocabulary diverges, or for automated cross-link suggestions. Always as a rerank/discovery layer over lexical, never a replacement.

## The mental model (canonical)

Every memory has two parts:

1. **The evidence** — the verbatim artifact: what was said out loud, the voice note, the document. Date-stamped, filed, immutable. A receipt.
2. **The meaning** — what the evidence tells us, incorporated into living pages (projects, lines of thinking, life areas). Every claim on a meaning page references its evidence: *"leaning toward the south-facing flat (see voice note, June 3)."*

And the brain has two roles:

1. **The librarian** — runs on every message: files the evidence, updates the meaning pages it touches.
2. **The compactor** — runs periodically (nightly/audit cadence): merges duplicates, connects pages that should know about each other, tightens bloat. Adds no information; organizes and makes connections.

Differentiation in one line: *Karpathy gave the world the recipe; we're opening the restaurant.*
